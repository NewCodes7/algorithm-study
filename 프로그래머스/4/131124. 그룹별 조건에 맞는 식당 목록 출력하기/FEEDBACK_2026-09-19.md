## 총평

회원별 리뷰 수를 집계한 뒤 해당 회원의 원본 리뷰들을 조회하는 큰 구조는 맞음.
최종 결과 한 행은 회원 한 명이 아니라 리뷰 한 건이라는 점을 올바르게 처리함.
다만 최다 작성자 동점 처리와 날짜 출력 형식 보완이 필요함.

이번에는 “제일 많이 쓴 고객이 여러 명이라면?”이라는 위험을 직접 발견함.
다음 단계는 발견한 의문을 반례로 확인하고 쿼리에 반영하는 것임.

## 기존 풀이와 비교

| 항목 | 기존 저장소 풀이 | 이번 사용자 풀이 |
| --- | --- | --- |
| 집계 후 원본 리뷰 조회 | 처리함 | 처리함 |
| 최다 회원 선택 | = + LIMIT 1 | IN + LIMIT 1 |
| 동점자 전체 선택 | 누락 가능 | 여전히 누락 가능 |
| 날짜 형식 | DATE_FORMAT 사용 | 원본 날짜 그대로 출력 |
| 리뷰 수 | COUNT(MEMBER_ID) | COUNT(REVIEW_ID) |
| 서브쿼리 구조 | 스칼라 서브쿼리 | 파생 테이블을 거친 IN 서브쿼리 |

- IN은 전달받은 집합에 포함되는지 확인하는 연산자임. 안쪽에서 LIMIT 1로 한 명만 남기면 동점자를 복구하지 못함.
- REVIEW_ID는 문제에서 NOT NULL이므로 COUNT(REVIEW_ID)와 COUNT(*)의 결과가 같음. 리뷰 행 수라는 의도는 COUNT(*)로 간단히 표현 가능함.
- SQL/mySQL.md에도 “가장 큰 걸 고르고 싶다면 LIMIT 1”이라는 메모가 있었음. 이번에 한 행 선택과 최댓값 전체 선택을 구분하도록 수정함.
- 날짜 형식은 예전 풀이에 있던 처리가 이번에 빠짐. 제출 직전에 출력 열, 형식, 정렬을 별도로 확인하기.

## 동점 반례

| 회원 | 리뷰 수 |
| --- | ---: |
| A | 2 |
| B | 2 |
| C | 1 |

- 필요한 결과: A의 리뷰 2건과 B의 리뷰 2건, 총 4건.
- 기존/이번 풀이: LIMIT 1로 A 또는 B 한 명만 선택되어 2건만 출력됨.
- 리뷰 수가 같은 경우 어느 회원이 먼저 선택되는지도 현재 ORDER BY만으로 보장되지 않음.
- 회원 ID를 정렬 조건에 추가해도 한 명을 고르는 순서만 정할 뿐, 동점자 누락은 해결되지 않음.
- 문제에는 최다 작성자가 한 명이라는 보장이 없음. 따라서 동점자를 모두 보존하도록 구현함. 숨은 채점 데이터에 동점자가 실제로 포함되는지는 확인하지 못함.

## 수정 풀이의 생각 순서

1. REVIEW_COUNTS: 회원별 리뷰 수를 구함. 결과 한 행은 회원 한 명.
2. MAX(CNT): 가장 많은 리뷰 수 하나를 구함.
3. CNT = MAX(CNT): 그 수와 같은 모든 회원 ID를 선택함.
4. 원본 REST_REVIEW에서 해당 회원의 리뷰를 모두 조회함. 결과 한 행은 리뷰 한 건.
5. MEMBER_PROFILE을 JOIN해 이름을 가져오고 날짜 형식과 정렬을 맞춤.

- WITH는 이번 쿼리에서 사용할 집계 결과에 이름을 붙이는 문법임. 물리적인 임시 테이블 생성이나 성능 향상을 보장한다는 뜻은 아님.
- MEMBER_ID가 NULL인 리뷰는 특정 회원으로 식별되지 않으므로 집계에서 제외함.
- DATE_FORMAT(R.REVIEW_DATE, '%Y-%m-%d')로 출력 형식을 지정함.
- ORDER BY R.REVIEW_DATE, R.REVIEW_TEXT로 실제 날짜와 리뷰 텍스트 순서로 정렬함.
- 바깥 쿼리를 다시 GROUP BY하거나 DISTINCT로 줄이면 필요한 개별 리뷰 행이 사라질 수 있음.

## IN 안쪽의 파생 테이블

이번 코드의 SELECT MEMBER_ID FROM (...) A는 무조건 불필요한 중첩이라고 볼 수 없음.
MySQL은 IN의 직접 서브쿼리에 LIMIT을 사용하는 형태를 제한함.

```sql
-- MySQL에서 제한되는 형태
WHERE MEMBER_ID IN (
    SELECT MEMBER_ID
    FROM REST_REVIEW
    GROUP BY MEMBER_ID
    ORDER BY COUNT(*) DESC
    LIMIT 1
)
```

이번 코드처럼 LIMIT이 있는 결과를 FROM의 파생 테이블로 감싸는 구조는 그 제한을 피하는 방식임.
하지만 그 안에서 이미 한 명만 선택했다는 논리 문제는 남음.
수정 풀이에서는 LIMIT을 없애고 최댓값과의 비교로 동점자를 보존함.

## 현재 동작을 유지하는 최소 리팩토링

최다 회원 한 명만 선택하는 현재 동작을 유지하려면 IN을 =로 바꾸고 중간 파생 테이블을 제거할 수 있음.
LIMIT 1 때문에 서브쿼리는 최대 한 행만 반환하므로 스칼라 비교가 가능함.
날짜 출력과 COUNT(REVIEW_ID)는 사용자 원문 그대로 유지함.

```sql
SELECT C.MEMBER_NAME, B.REVIEW_TEXT, B.REVIEW_DATE
FROM REST_REVIEW AS B
JOIN MEMBER_PROFILE AS C
    ON B.MEMBER_ID = C.MEMBER_ID
WHERE B.MEMBER_ID = (
    SELECT MEMBER_ID
    FROM REST_REVIEW
    GROUP BY MEMBER_ID
    ORDER BY COUNT(REVIEW_ID) DESC
    LIMIT 1
)
ORDER BY B.REVIEW_DATE, B.REVIEW_TEXT;
```

- IN의 직접 서브쿼리에서 LIMIT을 사용하는 제한은 이 스칼라 = 비교에 적용되지 않음.
- 최다 회원이 유일하면 원문과 같은 결과를 반환함. 동점일 때는 두 쿼리 모두 어떤 회원이 선택될지 보장하지 않으므로 정확히 같은 회원을 선택한다고 보장할 수는 없음.
- 원문의 빈 결과/NULL 비교 동작도 유지함. 서브쿼리가 빈 결과이거나 NULL을 반환하면 바깥 WHERE를 통과하는 리뷰가 없음.
- 목적은 중첩을 줄여 읽기 쉽게 만드는 것임. 실행 계획과 측정 없이 성능 향상을 단정하지 않음.
- 동점자 전체 조회와 날짜 형식 보완은 별도 변경이며, 이 최소 리팩토링에는 포함하지 않음. 저장소의 최종 SQL에는 앞에서 설명한 동점 처리·날짜 형식 보완을 반영함.

## 세미콜론 질문

- MySQL에서 완성된 SQL 문장 끝의 세미콜론은 정상적인 문장 종료 구분자임.
- 제시된 코드의 마지막 ORDER BY 뒤에 세미콜론 하나를 붙이는 것 자체를 SQL 문법 오류로 볼 수는 없음.
- 실제 오류 메시지와 당시 실행 SQL이 없어 이번 오류의 원인은 확정할 수 없음.
- 실행기가 쿼리 뒤에 내용을 덧붙이거나 쿼리를 감싸는 경우 등 실행 환경의 처리 방식은 가능한 원인이지만, 프로그래머스가 실제로 그렇게 동작했다고 확인한 것은 아님.
- 다시 발생하면 동일 코드에서 세미콜론 유무만 바꿔 비교하고, 오류 메시지의 위치를 보관하기.
- 'LIMIT & IN/ALL/ANY/SOME subquery' 오류라면 세미콜론과 별개인 위의 서브쿼리 제한 문제임.

```sql
SELECT C.MEMBER_NAME, B.REVIEW_TEXT, B.REVIEW_DATE
FROM REST_REVIEW B JOIN MEMBER_PROFILE C ON B.MEMBER_ID = C.MEMBER_ID
WHERE B.MEMBER_ID IN (SELECT MEMBER_ID FROM (SELECT MEMBER_ID, COUNT(REVIEW_ID) CNT
                                            FROM REST_REVIEW
                                            GROUP BY MEMBER_ID
                                            ORDER BY CNT DESC
                                            LIMIT 1) A)
```

## 기존 저장소 원문

```sql
SELECT A.MEMBER_NAME, B.REVIEW_TEXT, DATE_FORMAT(B.REVIEW_DATE, '%Y-%m-%d') AS REVIEW_DATE
FROM MEMBER_PROFILE AS A 
JOIN REST_REVIEW AS B
ON A.MEMBER_ID = B.MEMBER_ID
WHERE B.MEMBER_ID = (SELECT MEMBER_ID
                   FROM REST_REVIEW
                   GROUP BY MEMBER_ID
                   ORDER BY COUNT(MEMBER_ID) DESC
                   LIMIT 1)
ORDER BY B.REVIEW_DATE, B.REVIEW_TEXT
```
