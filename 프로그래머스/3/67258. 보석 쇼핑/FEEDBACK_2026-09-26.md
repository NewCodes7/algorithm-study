- [Java 파일](./보석 쇼핑.java): 직접 작성한 최종 코드와 원래 주석·회고를 보존하고, 요청한 피드백 3번(getOrDefault)을 추가함. 아래 정리한 코드는 별도 학습용 제안임.

## 1. 빠른 복습

- 포인터를 움직일 때 구간을 나타내는 집계 자료구조도 함께 갱신하기.
- 반복문이 중첩되었다고 바로 복잡도를 곱하지 말고, 전체 실행 동안 안쪽 코드가 총 몇 번 실행되는지 더해 보기.
- start가 되돌아가지 않고 최대 N번, end도 최대 N번 움직이면 합계는 최대 2N이므로 O(N).
- 개수를 누적할 때 map.put(key, map.getOrDefault(key, 0) + 1) 사용하기.
- getOrDefault는 조회만 하며, 없는 키를 자동으로 저장하지 않음.
- 풀이가 바로 떠오르지 않으면 작은 예시를 직접 실행하면서 유지할 조건과 포인터 이동 규칙을 찾아보기.

| 주제 | 기억할 내용 |
| --- | --- |
| 상태 일치 | 축소를 시작할 때 curr는 gems[start..end]의 정확한 보석 개수 |
| 구간 확장 | end 이동과 새 보석의 개수 증가를 한 묶음으로 처리 |
| 구간 축소 | 기존 왼쪽 보석의 개수 감소 후 start 이동 |
| 복잡도 | 반복문 겹수보다 전체 실행 횟수 합산 |
| 개수 누적 | getOrDefault(key, 0) + 1을 put으로 저장 |
| 동률 처리 | 더 짧을 때만 갱신하면 앞선 구간 유지 |

## 2. 풀이가 맞는 이유

먼저 모든 보석 종류를 포함하는 구간을 만든 뒤, 그 조건을 계속 유지하는 구조임.

각 end에서 왼쪽 보석의 개수가 2개 이상이면 하나 제거해도 모든 종류가 남음. 이를 최대한 반복하다가 왼쪽 보석이 1개가 되는 지점에서 멈춤. 그 보석까지 제거하면 조건이 깨지므로, 이 구간이 해당 end의 가장 짧은 유효 구간임.

이 과정을 end를 늘려 가며 반복하므로 전체 최단 구간을 찾을 수 있음. start는 뒤로 가지 않으며, 같은 길이에서는 정답을 바꾸지 않으므로 시작 번호가 가장 작은 구간이 유지됨.

원본의 curr.get(gems[end]) + 1도 안전함. 최초 구간에 이미 모든 종류의 키가 있고, 이후 개수를 0으로 만들거나 키를 제거하지 않기 때문임.

## 3. 시간복잡도: N × N인지 N + N인지

N은 보석 수, K는 보석 종류 수.

| 작업 | 전체 실행 동안의 최대 횟수 |
| --- | --- |
| 전체 종류 파악 | N번 |
| 최초 유효 구간 탐색 | N번 |
| end 증가 | N번 이하 |
| start 증가 | N번 이하 |

HashMap 연산을 평균 O(1)로 보면 전체 시간은 O(N), 추가 공간은 O(K).

중첩 반복문 안에서 start가 움직이더라도, 바깥 반복마다 0으로 돌아가지 않음. 어떤 반복에서 많이 움직이면 이후에 움직일 수 있는 거리가 그만큼 줄어듦.

대화에서 직접 정리한 이해:

> N²도 N을 N번 더한 것임. 덧셈 사고방식으로 접근하면 start가 N번만큼 움직이고 end도 N번만큼 움직이므로 2N이고, 상수를 떼면 N임.

앞으로는 “안쪽 코드가 끝까지 총 몇 번 실행되는가?”를 먼저 생각하기. 두 포인터가 모두 한 방향으로만 이동하고, 한 번 이동할 때 처리 비용이 평균 O(1)인 이 코드에서 위 계산이 성립함.

원래 메모의 수치만 보충하면, N = 100,000일 때 모든 연속 구간 수는 N(N + 1)/2 = 5,000,050,000개로 약 50억 개임. 모든 구간을 하나씩 보는 접근이 너무 크다는 판단은 맞음.

## 4. 개수 갱신 누락과 재발 방지

빠뜨렸던 줄:

```java
curr.put(gems[end], curr.get(gems[end]) + 1);
```

확인할 조건:

> 축소를 시작할 때 curr는 정확히 gems[start..end]의 보석 개수를 나타낸다.

단순히 “코드를 빼먹지 말자”보다 “포인터와 집계 상태가 일치하는지 확인하자”로 구체화하기.

| 구간 변화 | 필요한 처리 |
| --- | --- |
| 왼쪽 보석 제외 | 기존 gems[start] 개수 감소 → start++ |
| 오른쪽 보석 포함 | end++ → 범위 확인 → 새 gems[end] 개수 증가 |

누락을 드러내는 예시:

- 입력: [A, B, B, C, A]
- 최초 유효 구간: [1, 4]
- 올바른 최단 구간: [3, 5]
- 마지막 A의 개수를 반영하지 않으면 첫 번째 A를 제거할 수 없다고 판단하여 [1, 4]를 유지함.

역할을 드러내는 주석 예시:

```java
// 오른쪽 경계를 확장하고, 새로 포함한 보석 개수를 반영한다.
end++;
if (end == n) break;
curr.put(gems[end], curr.get(gems[end]) + 1);
```

## 5. 원본 주석에 추가한 피드백 3번: getOrDefault

```java
curr.put(gems[i], curr.getOrDefault(gems[i], 0) + 1);
```

getOrDefault(key, defaultValue)는 키가 있으면 매핑된 값을, 키가 없으면 지정한 기본값을 반환함.

| 조회 시 상태 | getOrDefault(gem, 0) 결과 | +1 후 put으로 저장할 값 |
| --- | --- | --- |
| 아직 없는 보석 | 0 | 1 |
| 현재 3개인 보석 | 3 | 4 |

기존 containsKey → get/put 또는 put(1) 분기를 한 줄로 표현할 수 있음. getOrDefault 자체는 조회만 하고, 저장은 put이 수행함. 참고로 키가 존재하면서 값이 null인 경우에는 기본값 대신 null을 반환함. 이 풀이에서는 null을 저장하지 않음.

## 6. 기존 아이디어를 유지한 코드 정리

최초 유효 구간을 찾는 반복문과 이후 구간을 확장하는 반복문을 합침. 매 반복의 첫 동작으로 새 보석의 개수를 반영하고, 모든 종류가 모이기 전에는 continue로 다음 보석을 확인함.

```java
import java.util.*;

class Solution {
    public int[] solution(String[] gems) {
        int typeCount = new HashSet<>(Arrays.asList(gems)).size();
        Map<String, Integer> counts = new HashMap<>();

        int start = 0;
        int answerStart = 0;
        int answerEnd = gems.length - 1;

        for (int end = 0; end < gems.length; end++) {
            // 오른쪽 보석을 현재 구간에 포함한다.
            String gem = gems[end];
            counts.put(gem, counts.getOrDefault(gem, 0) + 1);

            // 모든 종류가 모일 때까지 오른쪽으로 확장한다.
            if (counts.size() < typeCount) {
                continue;
            }

            // 모든 종류를 유지하면서 왼쪽을 최대한 줄인다.
            while (counts.get(gems[start]) > 1) {
                String leftGem = gems[start];
                counts.put(leftGem, counts.get(leftGem) - 1);
                start++;
            }

            // 더 짧을 때만 갱신하여, 길이가 같으면 앞선 구간을 유지한다.
            if (end - start < answerEnd - answerStart) {
                answerStart = start;
                answerEnd = end;
            }
        }

        return new int[] {answerStart + 1, answerEnd + 1};
    }
}
```

변경 이유:

- 전체 종류 수는 Set으로 구하고, 구간별 개수는 Map으로 관리함.
- 초기 구간 탐색과 이후 확장을 합쳐 보석을 추가하는 코드의 중복을 없앰.
- end 이동과 범위 검사는 for문에 맡김.
- getOrDefault로 개수 누적을 단순화함.
- start < end 조건은 제거해도 됨. 구간 길이가 1이면 해당 보석의 개수가 1이라 축소 조건에서 이미 멈춤.
- 원본의 사용하지 않는 set 변수는 정리한 코드에 남기지 않음.
- 평균 시간 O(N), 추가 공간 O(K)는 동일함.

## 7. 선택적 조기 종료

모든 종류를 담으려면 최소 K칸이 필요함. 유효 구간의 길이가 K가 되면 더 짧은 답은 없으므로, 정답 갱신 직후 아래 조건을 넣어도 됨.

```java
if (end - start + 1 == typeCount) break;
```

end를 앞에서부터 탐색하고 같은 길이에서는 기존 답을 유지하므로 동률 조건도 만족함. 이미 O(N)인 풀이이므로 필수 최적화는 아님.
