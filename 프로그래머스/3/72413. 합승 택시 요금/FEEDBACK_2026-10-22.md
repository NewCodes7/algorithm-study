## 2. 잘한 점 — sol1 → sol2 → sol3

사용자 메모에는 다음 사고의 전환이 남아 있음.

1. **sol1: 모든 경로를 나열해 겹치는 구간 비교** → 경우의 수가 커질 수 있고 경로 자체를 저장할 필요가 없음.
2. **sol2: 합승/개별 상태를 직접 관리하는 DP·BFS** → 상태 정의와 '헤어졌다가 다시 만나는 경우' 처리에 어려움을 느낌.
3. **sol3: 합승 종료 지점을 먼저 정하기** → 경로 시뮬레이션이 사라지고 독립된 최단거리 3개로 변환됨.

이 문제의 정답 식:

```text
min_{1 <= k <= n} [ d(s, k) + d(k, a) + d(k, b) ]
```

- `k = s`: 합승하지 않는 경우.
- `k = a` 또는 `k = b`: 한 사람의 목적지까지 동승하는 경우.
- 양방향 동일 요금 그래프이므로 `d(k,a)=d(a,k)`, `d(k,b)=d(b,k)`. 세 번의 단일 출발점 최단거리 계산으로 충분.
- 양수 요금 조건에서 헤어진 뒤 다시 합류하는 경로가 더 이득일 필요 없음. 구간을 함께 이동하면 각자 따로 지불한 두 비용보다 커지지 않으므로 **한 번 합승하다 갈라지는 형태의 최적해가 존재**.

**반복해서 적용할 설계 질문: '무엇 하나를 정하면 나머지가 쉬워질까?'** 그리고 후보별로 '고정할 것 / 필요한 값 / 계산 복잡도'를 적기.

## 3. 네 FIFO 큐 풀이 vs 다익스트라 — 결정적 차이

### 네 코드

```java
Queue<Integer> queue = new ArrayDeque<>();
// ...
if (c[0] != start && answer[c[0]] == 0 || cost < answer[c[0]]) {
    answer[c[0]] = cost;
    queue.offer(c[0]);
}
```

- **큐에 먼저 들어온 정점부터 처리**. 더 짧은 경로가 뒤늦게 나타나면 이전 정점을 또 큐에 넣어 이웃을 다시 검사함.
- **SPFA 계열 큐 기반 거리 완화 방식**으로 볼 수 있으나, 같은 정점의 큐 중복 삽입을 막지 않아 표준 SPFA의 최악 시간 상한을 그대로 적용하면 안 됨.
- 이 문제에서는 간선 요금이 양수이고, 비용이 줄어들 때 반복 전파하기 때문에 정답을 얻음. 하지만 일반 BFS의 `O(V+E)`가 보장되지는 않음.

### 우선순위 큐 다익스트라

- **지금까지 발견한 모든 미확정 정점 중 `출발점 → 그 정점` 누적 거리가 가장 작은 것**을 선택. 단순히 지금 노드의 이웃 간선 중 요금이 가장 작은 것을 선택하는 게 아님.
- 가중치가 0 이상이면 최소 누적 비용으로 꺼낸 정점의 최단거리가 확정됨. 그 정점에서의 거리 완화로 다른 후보들의 비용을 갱신.
- 이후 큐에서 꺼낸 값이 현재 `dist[node]`보다 크면 오래된 정보이므로 이웃을 스캔하지 않음.

예제 그래프: `1-2(10), 1-3(1), 3-2(1), 2-4(1)`. 1에서 출발할 때 거리는 `[0, 2, 1, 3]`(정점 1,2,3,4 순서).

- FIFO (간선을 1-2 먼저 등록): 유효 처리 순서 `1 → 2 → 3 → 4 → 2 → 4`; 2와 4 재처리.
- 다익스트라: `1 → 3 → 2 → 4` 순서로 확정; 이후 오래된 `(2,10)`은 건너뜀.
- 이 예시에서 이웃 간선 검사 수 FIFO 12회, 다익스트라 8회. **항상 이 비율로 빠르다는 뜻은 아니고, 재탐색을 줄인다는 예시**.

## 4. 기존 코드에서 개선할 부분 (오답과 개선 구분)

### (1) `0`을 두 가지 의미로 사용하지 않기

기존 `answer[]` 기본값 0이 **'아직 도달하지 않음'**과 **'출발점 거리 0'**을 동시에 표현함. 조건이 복잡해지는 원인.

```java
int[] dist = new int[graph.size()];
Arrays.fill(dist, INF);
dist[start] = 0;
```

이후 갱신 조건은 `if (nextCost < dist[next])` 하나면 충분.

### (2) 연산자 우선순위

기존 조건:

```java
c[0] != start && answer[c[0]] == 0 || cost < answer[c[0]]
```

실제 Java 평가 순서는:

```java
(c[0] != start && answer[c[0]] == 0) || (cost < answer[c[0]])
```

이 문제에서 양수 요금 및 출발점 거리 0 때문에 오답은 아니지만, 가독성이 낮고 일반화하기 어려움. `INF` 초기화로 해소 가능.

### (3) 합산에서 `distSum != 0`의 의미

원본은 `0`인 항목을 제외함. 이 문제는 **s에서 a, b로 이동 가능**하고 그래프가 무방향이므로, 어떤 정점 k는 세 출발점과 모두 연결되어 있거나 세 출발점 모두와 연결되어 있지 않음. 후자의 세 값은 원본 표현에서 모두 0이므로 현재 문제에서는 답이 맞음.

더 좋은 방식은 각각의 거리 값이 유효한지 검사하는 것:

```java
if (distS[k] == INF || distA[k] == INF || distB[k] == INF) continue;
```

### (4) 정점 번호는 1부터 n

원본 `for (i=0; i<distS.length; i++)`는 사용하지 않는 0번까지 순회. 의미가 드러나는 `for (int split=1; split<=n; split++)` 권장.

## 5. 기존 구조를 유지한 다익스트라 개선 코드 (원본을 덮어쓰지 않음)

```java
import java.util.*;

class Solution {
    private static final int INF = 1_000_000_000;

    public int solution(int n, int s, int a, int b, int[][] fares) {
        List<List<int[]>> graph = new ArrayList<>();
        for (int i = 0; i <= n; i++) graph.add(new ArrayList<>());

        for (int[] fare : fares) {
            int x = fare[0], y = fare[1], cost = fare[2];
            graph.get(x).add(new int[]{y, cost});
            graph.get(y).add(new int[]{x, cost});
        }

        int[] distS = dijkstra(s, graph);
        int[] distA = dijkstra(a, graph);
        int[] distB = dijkstra(b, graph);

        int answer = INF;
        for (int split = 1; split <= n; split++) {
            if (distS[split] == INF || distA[split] == INF || distB[split] == INF) continue;
            answer = Math.min(answer, distS[split] + distA[split] + distB[split]);
        }
        return answer;
    }

    private int[] dijkstra(int start, List<List<int[]>> graph) {
        int[] dist = new int[graph.size()];
        Arrays.fill(dist, INF);
        dist[start] = 0;

        // {정점, 출발지에서 이 정점까지의 누적 비용}
        PriorityQueue<int[]> pq =
                new PriorityQueue<>(Comparator.comparingInt(x -> x[1]));
        pq.offer(new int[]{start, 0});

        while (!pq.isEmpty()) {
            int[] state = pq.poll();
            int curr = state[0];
            int currCost = state[1];

            if (currCost > dist[curr]) continue; // 오래된 항목

            for (int[] edge : graph.get(curr)) {
                int next = edge[0];
                int nextCost = currCost + edge[1];
                if (nextCost < dist[next]) {
                    dist[next] = nextCost;
                    pq.offer(new int[]{next, nextCost});
                }
            }
        }
        return dist;
    }
}
```

복잡도: 인접 리스트+우선순위 큐를 이용한 다익스트라 3회는 이 문제의 단순 그래프에서 `O((V+E) log V)`; 공간 `O(V+E)`(그래프 포함).

## 6. 대안: 플로이드–워셜

- 모든 시작점/도착점 쌍에 대한 최단거리를 `dist[i][j]`라는 2차원 배열로 저장하는 **DP**.
- `k`를 경유지로 허용했을 때 더 짧아지는지 확인.

```java
for (int k = 1; k <= n; k++) {           // 경유지 — 가장 바깥
    for (int i = 1; i <= n; i++) {       // 시작점
        for (int j = 1; j <= n; j++) {   // 도착점
            if (dist[i][k] == INF || dist[k][j] == INF) continue;
            dist[i][j] = Math.min(dist[i][j], dist[i][k] + dist[k][j]);
        }
    }
}
```

초기화: `dist[i][j]=INF`, `dist[i][i]=0`, 간선 비용을 양방향으로 기록. 간선이 중복 제공될 수 있는 일반 문제라면 기존 값과 `Math.min` 처리.

**왜 k가 바깥인지:** k가 1부터 늘어나면서 '경유지로 1..k만 허용했을 때의 최단거리'라는 DP 단계가 완성되기 때문.

최종 비용은 `min_k(dist[s][k]+dist[k][a]+dist[k][b])`.

복잡도: `O(V^3)` 시간, `O(V^2)` 공간. 이 문제는 `n<=200`이므로 삼중 반복의 핵심 횟수가 최대 `200^3=8,000,000`회라 충분히 검토 가능.

## 7. 인접 리스트 vs 인접 행렬 — 선택 기준

| 작업 | 인접 리스트 | 인접 행렬 |
| --- | --- | --- |
| 그래프 저장 | `O(V+E)` | `O(V^2)` |
| 한 정점의 모든 이웃 확인 | `O(deg(v))` | `O(V)` |
| 두 정점의 직접 연결 여부 / 간선 비용 조회 | 일반 리스트 `O(deg(v))` | `O(1)` |

이웃을 빈번히 순회하는 다익스트라에는 인접 리스트가 자연스럽고, 플로이드–워셜처럼 모든 정점 쌍을 갱신할 때는 2차원 행렬이 자연스러움. 인접 행렬이 모든 상황에서 더 빠른 것은 아님.

## 8. 다음 무힌트 재풀이 체크리스트

- [ ] `k=s`, `k=a`, `k=b`를 포함해 합승 지점 하나를 고정하는 이유 스스로 설명
- [ ] `distS`, `distA`, `distB` 세 배열을 **우선순위 큐 다익스트라**로 직접 작성
- [ ] PQ가 **현재 이웃 중 최소 비용이 아니라 전체 미확정 후보의 최소 누적 비용**을 선택하는 이유 설명
- [ ] `INF` 초기화, `dist[start]=0`, 오래된 항목 `continue` 포함
- [ ] `k, i, j` 순서의 플로이드–워셜을 코드 없이 점화식부터 도출
- [ ] 두 알고리즘의 시간복잡도 및 인접 리스트/행렬 사용 이유 설명

**풀이 태도:** 설계가 막막해도 sol1/sol2/sol3을 구분해 적고, 계산할 결과만 남기도록 상태를 단순화하는 관점을 버리지 않기. '설계에 쫄지 말아야 하는 이유!'라는 원래 깨달음을 보존함.
