## 1. 접근과 백트래킹

- `type[i]`는 유형 `i`에 배정한 멘토 수. 모든 유형에 최소 한 명 필요하므로 1로 시작함.
- 깊이 `n-k`까지 멘토를 하나씩 더 배정하고, 완료 시 전체 대기시간 `judge(type)`를 구해 최솟값을 갱신함.
- `start` 이상부터 반복하고 재귀호출에 `i`를 전달하므로, 예를 들어 1→2와 2→1 같은 **같은 최종 배분의 중복 순열**을 세지 않음.
- `i+1`을 전달하면 같은 유형에 추가 멘토를 여러 명 배정할 수 없으므로 오답.
- 배분 수는 **C(n-1, k-1)**. 최대 `n=20`, `k=5`에서 **C(19,4)=3,876**으로, 완전탐색이 충분히 작음.

## 2. 우선순위 큐 시뮬레이션

현재 구현:
```java
int t = pq.poll();
if (a >= t) {
    pq.offer(a + b);
} else {
    pq.offer(t + b);
    time += t - a;
}
```

동일한 의미의 간결한 표현:
```java
int t = pq.poll();
time += Math.max(0, t - a);
pq.offer(Math.max(a, t) + b);
```

- `pq`에는 각 멘토가 다음 상담을 시작할 수 있는 시각(기존 상담 종료 시각)을 저장.
- 처음에는 멘토 수만큼 0을 삽입.
- 각 상담 유형 내에서 시각순으로 도착하는 참가자를 처리하고, 가장 빨리 비는 멘토를 선택하면 대기시간 최소화를 정확하게 시뮬레이션할 수 있음.
- `PriorityQueue<Integer>`의 기본 정렬은 오름차순(최소 힙). `poll()`로 최솟값 추출.

## 3. 정렬 실수에서 얻을 교훈

처음 코드에서는 상담 유형 `c` 및 요청 시각 `a` 기준으로 수동 정렬을 구현했으나, 문제에서 **전체 `reqs`의 요청 시각 오름차순이 이미 보장**됨.

지금처럼 각 유형 `i`에 대해 전체 `reqs`를 순회하면서 `c != i`를 건너뛰어도, 해당 유형 요청들의 시간순서가 보존됨. 따라서 최종 코드의 `reqsSorted = reqs`가 맞고, 추가 정렬은 불필요.

일반적인 2차원 배열 정렬 문법은 기억:
```java
Arrays.sort(reqs, (x, y) -> {
    if (x[2] != y[2]) return Integer.compare(x[2], y[2]);
    return Integer.compare(x[0], y[0]);
});
```

간결한 체이닝 버전:
```java
Arrays.sort(reqs,
    Comparator.comparingInt((int[] x) -> x[2])
              .thenComparingInt(x -> x[0]));
```

정렬 기준이 여러 개라면 첫 기준이 같을 때 다음 기준으로 넘어감. `Integer.compare()`를 사용하면 뺄셈 비교의 오버플로 위험도 피할 수 있음.

**실전 습관:** 구현 시작 전에 요청/구간/그래프 등이 이미 정렬되어 있는지, 중복이 가능한지, 상한이 얼마인지 먼저 확인하기.

## 4. 복잡도 및 개선 방향

- 조합 수: `C(n-1,k-1)`.
- 현재 `judge()` 한 번은 각 유형에 대해 `reqs` 전체를 확인하므로 `O(kR + R log n + n)` 정도 (`R=reqs.length`). 멘토 힙 합계 초기화도 포함.
- 총 계산량은 최대 조합 수를 곱한 `O(C(n-1,k-1) × (kR + R log n + n))`. 현재 제약에서 충분히 실행 가능.
- 같은 유형에 멘토 `m`명을 배정했을 때 그 유형의 대기시간은 **다른 유형에 몇 명 배정했는지 무관**.
- 따라서 `wait[type][m]`을 미리 계산한 뒤, 배분 조합의 점수를 대기시간 테이블 합으로 구해 반복 작업을 줄일 수 있음.
- 발전시키면 `dp[type][usedMentors]`: 앞에서 `type`개 유형까지 `usedMentors`명을 배정했을 때의 최소 대기시간. 다음 유형에 `m`명을 배정하면서 `wait[type+1][m]`을 더하는 자원 배분 DP가 가능.

## 5. 작은 안전성 개선(원본은 그대로 유지)

클래스 필드인 `answer`가 생성자 시점에 한 번만 `Integer.MAX_VALUE`로 초기화됨. 같은 `Solution` 객체에서 `solution()`을 다시 호출할 때 이전 최솟값이 남을 수 있음. 재사용 가능한 코드로 만들 때는 시작 부분에서 `answer = Integer.MAX_VALUE;`를 다시 실행하는 편이 안전.

또한 `reqsSorted`는 이제 실제로 정렬한 사본이 아닌 `reqs` 참조이므로 이름을 단순히 `reqs`로 바꾸면 의도가 더 명확하지만, 사용자가 작성한 원본은 보존함.

## 복습 체크리스트

- [ ] 순서가 중요하지 않은 인원 배분을 중복 조합으로 구현하고 `start=i`인 이유 설명
- [ ] `PriorityQueue`에 상담 완료시각을 넣고 최소값을 꺼내는 이유 설명
- [ ] 대기시간 `max(0,t-a)`, 종료시각 `max(a,t)+b`를 직접 작성
- [ ] 이미 정렬된 입력인지를 제한사항에서 발견
- [ ] `Arrays.sort()` + `Comparator`로 다중 기준 2차원 배열 정렬 가능
- [ ] 반복되는 유형별 시뮬레이션을 메모이제이션/DP로 분리할 수 있는지 생각
