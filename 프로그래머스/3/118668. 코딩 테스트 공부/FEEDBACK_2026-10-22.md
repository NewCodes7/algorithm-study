## 1. 실전에서 DP를 떠올리는 방법

처음부터 점화식을 외워서 끼워 맞추려 하지 말기. 먼저 완전탐색으로 생각해보기.

1. **가능한 행동 나열:** 알고력 공부, 코딩력 공부, 현재 풀 수 있는 문제 풀기.
2. **중복 상황 찾기:** 행동 순서는 달라도 같은 `(알고력, 코딩력)`에 도착할 수 있음.
3. **과거가 필요한지 질문:** 현재 능력치가 같다면 앞으로 풀 수 있는 문제와 행동 비용도 같음. 같은 문제는 반복해서 풀 수 있으므로 어떤 문제를 이미 풀었는지 기록할 필요도 없음.
4. **최적값 하나만 남기기:** `(10, 10)`까지 7시간과 12시간이 걸린 두 경로가 있다면 7시간만 남겨도 됨. 이후 어떤 행동을 이어 붙여도 12시간 경로가 유리해지지 않음.
5. **상태 수·전이·계산 순서 확인:** 합칠 수 있다는 생각에서 끝내지 말고 실제로 작은 배열로 표현하고 필요한 이전 값을 먼저 계산할 수 있는지 확인하기.

실전에서 적어볼 세 질문:

```text
앞으로 가능한 선택을 결정하려면 어떤 정보가 필요한가?
그 정보가 같다면 어떤 경로 하나만 남겨도 되는가?
그 상태들을 어떤 순서로 계산할 수 있는가?
```

최솟값을 묻는다는 이유 하나만으로 DP라고 결정하지 않기. **반복해서 만나는 상태와 안전하게 버릴 경로**를 먼저 찾기.

## 2. 상태와 저장할 값을 구분하기

```java
dp[a][c] = 알고력 a, 코딩력 c에 도달하는 최소 시간
```

상한 처리를 한 뒤에는 정확히는 `(min(실제 알고력, 목표 알고력), min(실제 코딩력, 목표 코딩력))`으로 표현한 상태에 도달하는 최소 시간임.

| 구분 | 이번 문제 |
|---|---|
| 앞으로 가능한 행동을 결정하는 정보 | 알고력·코딩력 |
| 같은 상태에서 비교해서 남길 값 | 최소 소요 시간 |
| 정답에 필요 없는 정보 | 세부 행동 순서, 이미 풀었던 문제 목록 |

시간이 같다고 가능한 행동까지 같은 것은 아님. 그래서 시간만으로 상황을 합칠 수는 없고, 시간별 능력치 조합을 따로 관리해야 함. 시간 기준 탐색도 가능하지만 이번에는 능력치별 최소 시간을 저장하는 편이 간단했음.

**상태를 정하는 것과 처리 순서를 정하는 것은 별개의 선택!** 같은 `(a, c)` 상태를 일반 DP로도, 다익스트라로도 처리할 수 있음.

## 3. 점화식은 가능한 행동을 코드로 옮긴 것

`dp[2][3] = 5`라면 현재 능력치에 오는 최소 시간이 5라는 뜻.

| 행동 | 다음 상태 | 새로 찾은 시간 |
|---|---|---|
| 알고력 공부 | `(3, 3)` | `5 + 1` |
| 코딩력 공부 | `(2, 4)` | `5 + 1` |
| 보상 `(2, 1)`, 비용 3인 문제 풀기 | `(4, 4)` | `5 + 3` |

이전에 더 빠른 경로가 발견됐을 수 있으니 덮어쓰지 말고 `min`으로 갱신!

```java
dp[a + 1][c] = Math.min(dp[a + 1][c], dp[a][c] + 1);
dp[a][c + 1] = Math.min(dp[a][c + 1], dp[a][c] + 1);

// 현재 능력치로 풀 수 있는 문제에 대해서만 수행
int nextAlp = Math.min(targetAlp, a + problem[2]);
int nextCop = Math.min(targetCop, c + problem[3]);
dp[nextAlp][nextCop] = Math.min(
    dp[nextAlp][nextCop], dp[a][c] + problem[4]
);
```

공부 전이에는 목표 범위 검사도 필요함. 사용자 원본은 배열을 `+2`로 만들어 안전하게 접근하고, 개선안은 `a < targetAlp`, `c < targetCop`으로 제한함.

원본 주석의 `dp[3][2] = dp[2][2] + 1`은 **가능한 경로 하나의 비용**을 나타냄. 다른 경로도 있을 수 있으므로 실제 갱신식에는 `Math.min()`이 필요함.

## 4. 왜 능력치 오름차순으로 한 번만 순회해도 되나?

```java
for (int a = startAlp; a <= targetAlp; a++) {
    for (int c = startCop; c <= targetCop; c++) {
        // 현재 칸의 최소 시간을 가능한 다음 칸에 전달
    }
}
```

모든 행동은 알고력과 코딩력을 감소시키지 않음.

- 알고력이 증가하면 나중에 처리할 행으로 이동함.
- 알고력이 같고 코딩력이 증가하면 현재 행의 나중 칸으로 이동함.
- 둘 다 같으면 자기 자신으로 돌아오는 행동인데, 비용이 양수이므로 개선하지 못함.

따라서 실제로 값을 개선하는 전이는 항상 순회상 뒤쪽을 향함. 현재 칸을 처리할 때, 그 칸으로 들어오는 유효한 전이의 출발 상태들은 이미 처리되어 있음. 나중 칸에서 돌아와 현재 칸을 더 좋게 바꿀 일이 없음.

자기 자신으로 돌아오는 간선을 제외하면 DAG의 위상 순서대로 최단 비용을 계산하는 것과 같음. **이번 DP에서 우선순위 큐가 필요 없는 이유**임.

능력치가 줄어드는 행동이 추가된다면 이 순회 근거가 깨짐. 그때는 같은 반복문을 그대로 적용하면 안 됨.

## 5. 모든 경로를 끝까지 탐색하는 것과 DP의 차이

원본 메모의 다음 두 표현을 더 정확하게 기억하기.

- “모든 경우의 수 계산” → 각 상태에서 가능한 모든 행동을 검토하되, 같은 상태에 도착한 경로는 최소 시간 하나로 합침.
- “그 상황에서 할 수 있는 최선” → 당장 유리해 보이는 행동 하나를 고르는 게 아니라, 모든 행동의 결과를 각 도착 칸에 전달함.

알고력 공부와 문제 풀이 중 무엇이 최종적으로 유리할지 지금 하나로 결정하지 않음. 도착 상태별로 최솟값을 누적하면서 전체 최적해를 구함.

## 6. 목표를 초과한 상태는 버리지 말고 합치기

목표 알고력이 20이라면 `(20, 10)`과 `(100, 10)`에서 풀 수 있는 문제와 각 행동의 비용은 같음. 요구 능력치가 20보다 높은 문제가 없기 때문.

```java
alp = Math.min(alp, targetAlp);
cop = Math.min(cop, targetCop);

int nextAlp = Math.min(targetAlp, a + alpReward);
int nextCop = Math.min(targetCop, c + copReward);
```

**시작점·공부·문제 보상 모두 같은 상태 범위를 지켜야 함.** 공부는 경계 검사로 목표 이상 올리지 않아도 됨.

초기값을 빠뜨렸던 반례:

```java
alp = 10;
cop = 0;
problems = new int[][]{{5, 5, 1, 1, 1}};
// 목표는 (5, 5), 정답은 5.
// dp[6][6]에 초기 (10, 0)을 그대로 접근하면 배열 범위 초과!
```

원본 주석의 “알고력과 코딩력은 최대 150”은 보완 필요! **초기 능력치와 요구 능력치의 상한이 150**임. 실제 능력치는 보상·공부로 더 커질 수 있고, 이번 풀이가 목표로 합쳐 저장하는 것임.

`int[10000][10000]`은 원소만 약 400MB이고 초기화에 1억 번의 대입이 필요함. 목표로 합치면 상태는 최대 `151 × 151 = 22,801`개. 복잡한 가지치기 전에 필요한 상태 공간부터 계산하기!

## 7. 다익스트라의 두 기록 방식을 섞지 않기

정점은 `(알고력, 코딩력)`, 간선은 공부·문제 풀이, 가중치는 소요 시간. 모든 비용이 양수이므로 다익스트라로도 해결 가능함.

| 구분 | 사용자 다익스트라 원본 | 개선 다익스트라 |
|---|---|---|
| 배열 의미 | 이미 확정한 최소 시간 | 지금까지 발견한 최소 시간 |
| 기록 시점 | 큐에서 꺼낸 뒤 처음 처리할 때 | 더 짧은 경로를 발견해 넣기 직전 |
| 시작점 배열 값 | `INF` 유지 | `0`으로 설정 |
| 꺼낸 항목을 건너뛰는 조건 | `time >= dp[a][c]` | `time > dist[a][c]` |
| `time == 배열 값` | 이미 확정했으므로 중복 처리 방지 | 현재 최선 경로이므로 정상 처리 |

사용자 원본은 다음 의미로 이해하면 정확함.

```java
if (time >= dp[a][c]) {
    continue;
}
dp[a][c] = time; // 이 상태를 처음 처리할 때 최단 시간 확정
```

시작점 `dp`를 미리 0으로 두면 시작점부터 건너뛰므로 주의!

개선안은 넣기 전에 기록함.

```java
if (nextTime < dist[nextAlp][nextCop]) {
    dist[nextAlp][nextCop] = nextTime;
    pq.offer(new int[]{nextAlp, nextCop, nextTime});
}

// 나중에 꺼냈을 때
if (time > dist[a][c]) {
    continue; // 큐에 넣은 뒤 더 좋은 경로가 발견된 오래된 항목
}
```

같은 상태의 7시간 경로를 이미 큐에 넣었다면 아직 꺼내기 전이어도 10시간 경로는 삽입하지 않음. 사용자 방식도 올바르지만, 개선안은 아직 확정되지 않은 상태의 불필요한 삽입도 줄임.

원본의 “그 사이 더 최소가 할당됐을 수 있음”보다 **“이 상태는 이미 최소 시간으로 확정했을 수 있으므로 다시 확장하지 않음”**이 그 구현의 정확한 설명임.

원본 메모의 “cost는 더 낮아질 수 없음”은 **하나의 경로를 계속 따라갈 때 누적 시간이 감소하지 않는다**는 뜻으로 이해하기. 같은 상태에 대해 지금까지 발견한 최소 시간은 더 빠른 다른 경로를 찾으면 낮아질 수 있음. 그래서 확정 시점과 갱신 시점을 구분해야 함.

## 8. 목표를 처음 넣었을 때가 아니라 꺼냈을 때 종료

다익스트라에서 목표에 도달하는 경로를 발견했다고 곧바로 최적은 아님. 아직 큐에 더 싼 경로의 중간 상태가 남아 있을 수 있음.

오래된 항목을 걸러낸 후, 목표 상태를 최소 시간으로 **꺼냈을 때** 반환하기. 원본과 개선안 모두 이 순서를 지킴.

## 9. PriorityQueue와 Comparator 문법

배열에는 기본적인 크기 비교 순서가 없으므로 비교 기준을 지정해야 함.

```java
// 원소 하나에서 정수 키 추출 → 그 키를 비교하는 Comparator 생성
PriorityQueue<int[]> pq =
    new PriorityQueue<>(Comparator.comparingInt(a -> a[2]));

// 두 원소를 받아 직접 비교
PriorityQueue<int[]> pq2 =
    new PriorityQueue<>((a, b) -> Integer.compare(a[2], b[2]));
```

처음 오류가 났던 형태:

```java
// 잘못된 형태
new PriorityQueue<>(a -> Comparator.comparingInt(a[2]));
```

- `a -> a[2]`: 배열 하나에서 비교할 값을 꺼내는 함수.
- `Comparator.comparingInt(...)`: 위 함수를 받아 Comparator를 만들어 줌.
- Comparator 자체는 두 원소를 비교하는 `compare(a, b)` 규칙임.
- `comparingInt(a[2])`처럼 숫자를 넣거나, 완성된 Comparator 바깥에 불필요한 `a ->`를 붙이지 않기.
- 정수 비교는 `a[2] - b[2]`보다 `Integer.compare()` 사용. 일반적인 큰 정수에서 뺄셈 오버플로 방지.

주요 생성자 형태:

| 코드 | 의미 |
|---|---|
| `new PriorityQueue<Integer>()` | 기본 순서, 작은 정수부터 |
| `new PriorityQueue<Integer>(100)` | 초기 용량 100. 최대 크기 제한이 아님 |
| `new PriorityQueue<int[]>(cmp)` | 지정한 비교 규칙 |
| `new PriorityQueue<int[]>(100, cmp)` | 초기 용량과 비교 규칙 지정 |
| `new PriorityQueue<Integer>(List.of(3, 1, 2))` | 주어진 원소로 구성 |

큐는 필요하면 커지고, 같은 우선순위 원소의 순서는 보장하지 않음. `for-each`로 돌았을 때 정렬 순서가 되는 것도 아님. 우선순위 순서로 꺼내려면 `poll()` 사용.

## 10. continue·break·return의 적용 범위

그냥 `continue`는 가장 가까운 반복문의 다음 반복으로 이동함. `while` 안에 중첩 `for`가 있어도 바깥 `while`로 바로 이동하지 않음.

```java
outer:
while (!pq.isEmpty()) {
    int[] state = pq.poll();
    for (int value : state) {
        if (value < 0) {
            continue outer; // while의 다음 반복으로 이동
        }
    }
    // 값 검사를 모두 통과한 상태만 처리
}
```

| 문법 | 효과 |
|---|---|
| `continue;` | 가장 안쪽 반복문의 다음 반복 |
| `continue outer;` | 라벨이 붙은 반복문의 다음 반복 |
| `break outer;` | 라벨이 붙은 구문 종료 |
| `return;` / `return 값;` | 현재 메서드 종료 |

비용·능력치 지배 관계를 확인하려고 모든 주변 칸을 매번 중첩 순회하면 그 검사 자체가 비싸짐. 이번에는 동일 상태의 최솟값 저장과 상한 처리만으로 해결 가능했음.

## 11. 초기화·배열 경계·예외 처리

- 사용자 DP 원본의 `+2` 배열은 공부 결과를 목표 바로 바깥에 저장하지만 그 칸을 순회하지 않으므로 정답에 영향 없음. 개선안은 `+1` 배열과 경계 검사로 사용하지 않는 칸을 줄임.
- 원본의 `int answer = 0`은 미사용 변수. 개선안에서 제거함.
- `Arrays.fill(row, Integer.MAX_VALUE)`로 행별 초기화를 간결하게 작성 가능.
- `Integer.MAX_VALUE + 비용`은 일반적으로 오버플로 위험이 있음. 다만 **이번 DP는 시작점에서 목표까지의 직사각형 안 모든 상태에 공부만으로 도달**하므로, 해당 칸을 처리할 때는 이미 유한한 값임. 현재 코드에 오버플로 오류가 있다고 지적하면 안 됨.
- 다른 DP에서 도달 불가능한 상태도 순회한다면 `if (dp[a][c] == INF) continue;` 등의 처리가 필요할 수 있음.
- 예외를 잡은 뒤 `return 0`으로 넘어가면 실패를 정상 결과처럼 숨김. 이번 `try-catch`는 제거하는 게 좋았음. 자세한 발생 위치가 필요하면 `e.printStackTrace()`로 확인 가능.
- 다익스트라 원본의 마지막 `return 0`은 모든 상태를 탐색해도 답을 못 찾는 경우에 해당하나, 이 문제는 공부만으로 도달하므로 실행되지 않음. 개선안은 이 의미를 `return -1`로 표현함.

## 12. 복잡도와 다음 실전에서의 적용

`A`, `C`를 목표 알고력·코딩력, `P`를 문제 수, `V = (A + 1)(C + 1)`로 두면:

| 풀이 | 시간 | 추가 공간 |
|---|---|---|
| 오름차순 2차원 DP | `O(V(P + 1))` | `O(V)` |
| 중복 큐 항목을 허용하는 다익스트라 | `O(V(P + 1) log(2 + V(P + 1)))` 상한 | 배열 `O(V)`, 큐는 최악 `O(V(P + 1))` |

문제 수가 최소 1이므로 보통 DP를 `O(VP)`라고 줄여 씀. 이 문제는 `A, C ≤ 150`, `P ≤ 100`으로 상태 수를 충분히 줄일 수 있음.

다음 실전에서의 순서:

1. 가능한 행동을 완전탐색 관점에서 나열.
2. 서로 다른 경로가 같은 상황으로 합쳐지는지 확인.
3. 미래 선택을 결정하는 정보만 상태로, 비교할 최적값은 배열 값으로 구분.
4. 각 행동을 `min` 갱신으로 작성.
5. 상태 수와 배열 경계 확인. 상한으로 합칠 수 있다면 초기 상태까지 일관되게 적용.
6. 먼저 계산할 상태의 순서를 증명. 이번처럼 되돌아가는 유효한 전이가 없다면 보텀업 DP 검토.
7. 그런 순회가 불가능하고 비용이 음수가 없다면 다익스트라 같은 최단 경로 접근 검토.
