## 1. 30초 복습 — 다음 문제에도 적용할 피드백

| 상황 | 기억할 점 |
|---|---|
| **범위마다 같은 값 증가** | 모든 칸을 반복 갱신하지 말고 **차분 배열**로 시작에 `+1`, 끝에 `-1` 기록 |
| 차분 배열의 값이 필요함 | **누적합**으로 특정 시각의 실제 시청자 수 복원 |
| **고정 길이 구간의 합**을 여러 번 구함 | 이전 합에서 나가는 원소를 빼고 들어오는 원소를 더하는 **슬라이딩 윈도우** |

| 구간의 길이와 인덱스 | 시작 포함·끝 제외인 **반열린 구간 `[start, end)`**, 길이는 `end-start` |
| 시청시간 등 큰 값을 합산 | `int`가 아닌 **`long`** 여부를 최대값으로 판단. 곱셈 **중간 결과**도 주의 |
| 같은 합이면 빠른 시작 시각 | 시작 시각 오름차순 탐색 + `sum > maxSum`일 때만 갱신 |
| 구간 데이터 구조 선택 | **업데이트 전부 → 조회**인지, **업데이트 ↔ 조회가 번갈아** 발생하는지 먼저 구분 |

## 2. 병목을 없앤 결정적 아이디어 — '모든 칸' 대신 '변화하는 경계'

처음 구현은 로그마다 `[start, end)`의 초를 전부 순회했음.

```java
for (int j = start; j < end; j++) {
    stats[j]++;
}
```

로그 수 `L ≤ 300,000`, 시간축 크기 `T ≈ 360,000`이므로 최악 `O(L×T)`, 대략 **1,080억 회**의 초 단위 갱신이 발생할 수 있음.

개선된 원본:

```java
stats[start]++;
stats[end]--;
```

- `stats[t]`는 **그 초에 시청하는 사람 수가 아니라 사람 수의 변화량**.
- 예: `[2,5)`에 +1이면 2초에 +1, 5초에 -1. 실제 2·3·4초만 시청자로 잡힘.
- `viewers(t) = stats[0] + stats[1] + ... + stats[t]`로 복원.
- 로그 1개 처리 비용이 `O(T)`에서 `O(1)`로 줄어듦.

**일반화:** 모든 범위 업데이트를 모아 놓고 나중에 값을 계산할 수 있다면 차분 배열을 고려한다. `diff[L] += x; diff[R] -= x`는 `[L,R)` 전체에 `x`를 더하는 효과가 있음.

## 3. 직접 작성한 코드의 좋은 점 — 두 개의 누적값과 슬라이딩 윈도우

사용자는 차분 배열을 따로 복원하지 않고, 필요한 위치의 시청자 수를 **이동 중에 누적 계산**함.

```java
inTimeStart += stats[i - 1];
inTimeEnd += stats[i + advTime - 1];
sum = beforeSum - inTimeStart + inTimeEnd;
```

각 변수의 불변식:

| 변수 | i번째 광고 시작 시각을 검사할 때 의미 |
|---|---|
| `inTimeStart` | **떠나는 시각 `i-1`**에서 실제 시청자 수 |
| `inTimeEnd` | **들어오는 시각 `i+advTime-1`**에서 실제 시청자 수 |
| `beforeSum` | 직전 광고 구간 `[i-1, i-1+advTime)`의 누적 시청시간 |
| `sum` | 새 광고 구간 `[i, i+advTime)`의 누적 시청시간 |

즉 **새 구간 합 = 이전 구간 합 - 빠지는 값 + 들어오는 값**.

첫 구간을 계산하는 코드도 올바름:

```java
for (int j = 0; j < advTime; j++) {
    inTimeEnd += stats[j]; // viewers(j)
    maxSum += inTimeEnd;
}
```

이 접근은 정확하고 공간 효율도 좋음. 다만 누적 상태를 여러 개 유지하므로 실전 가독성과 디버깅 난이도는 다소 높아짐.

## 4. 같은 복잡도로 더 단순하게 작성하기 (참고 코드 — 원본은 변경하지 않음)

차분 배열을 실제 시청자 수 배열로 먼저 복원하면 슬라이딩 윈도우가 더 명확해짐.

```java
// 각 시점 변화량(diff) -> 실제 시청자 수
for (int t = 1; t < totalTime; t++) {
    stats[t] += stats[t - 1];
}

// 첫 번째 광고 구간 [0, advTime)
long windowSum = 0;
for (int t = 0; t < advTime; t++) {
    windowSum += stats[t];
}
long maxSum = windowSum;
int startTime = 0;

// 한 칸씩 이동
for (int start = 1; start + advTime <= totalTime; start++) {
    windowSum -= stats[start - 1];
    windowSum += stats[start + advTime - 1];
    if (windowSum > maxSum) {
        maxSum = windowSum;
        startTime = start;
    }
}
```

복잡도는 **원본과 동일한 시간 `O(L+T)`, 추가 공간 `O(T)`**. 원본처럼 한 번에 누적해도 정답이며, 위 코드는 가독성을 위한 대안임.

## 5. 실수 방지 — 구간, 자료형, 동률

### (1) 반열린 구간 `[start, end)`

사용자 주석의 '열린 구간'은 정확히는 **반열린 구간**임. 시작은 포함, 종료는 제외하므로 길이가 `end-start`가 되고 마지막 포함 인덱스는 `end-1`임.

광고 길이 `advTime`, 시작 `i`라면 새롭게 들어오는 초는 `i + advTime - 1`임. 무작정 `<=`를 쓰지 말고 작은 숫자로 구간을 그려 확인.

### (2) `long`은 '최댓값 × 누적 개수'를 보고 결정

매초 시청자 수는 최대 300,000명이므로 `int[] stats`로 충분함. 반면 누적 시청시간은 약 `360,000 × 300,000 = 108,000,000,000`초까지 가능해 `int` 범위를 초과함.

```java
long total = (long) a * b; // 두 int의 곱셈 중간 연산도 long으로
// long total = a * b;     // int 곱셈에서 먼저 오버플로가 날 수 있음
```

### (3) 동률에서는 원래 답을 유지

광고 시작을 0부터 오름차순으로 탐색하고 `sum > maxSum`일 때만 수정하므로, 같은 누적 재생시간이라면 가장 빠른 시작 시각을 유지함.

## 6. 차분 배열·누적합·펜윅 트리·세그먼트 트리 선택 기준

후속 복습에서 '특정 값의 빠른 조회가 필요할 때는 다른 자료구조가 필요'하다는 가설을 세웠음. **특정 값 조회 자체가 문제인 것은 아님. 업데이트와 조회가 교차하는지가 핵심**임.

| 작업 패턴 | 적절한 선택 | 복잡도(일반적) |
|---|---|---|
| 구간 업데이트 전부 완료 → 특정 값 여러 번 조회 | 차분 배열 + 누적합으로 배열 복원 | 업데이트 각 `O(1)`, 복원 `O(N)`, 점 조회 `O(1)` |
| 구간 업데이트 전부 완료 → 구간 합 여러 번 조회 | 복원 후 **두 번째 누적합** | 전처리 `O(N)`, 구간 합 `O(1)` |
| 구간 업데이트 ↔ 특정 값 조회가 번갈아 | 차분 배열 위에 **펜윅 트리**로 변화량 관리 | 구간 업데이트 `O(log N)`, 점 조회 `O(log N)` |
| 특정 위치 증가 ↔ 구간 합 조회가 번갈아 | **펜윅 트리** 또는 세그먼트 트리 | 둘 다 `O(log N)` |
| 구간 증가 ↔ 구간 합/최댓값/최솟값 조회가 번갈아 | **Lazy Segment Tree** (연산에 맞게 구현) | 둘 다 `O(log N)` |

즉, **정적인 대량 구간 갱신은 차분 배열**, **동적인 갱신과 조회의 교대는 트리 자료구조**를 검토. 광고 삽입은 모든 로그를 먼저 반영하고 마지막에 최적 광고 구간을 구하므로 차분 배열로 충분함.

## 7. 풀이 태도: 이번에 사용자가 직접 남긴 교훈

원본 코드 하단 메모의 다음 내용을 다른 문제에도 적용하도록 정리함.

1. **문제 예시의 계산식을 잘 읽기.** `[start,end)`처럼 포함/제외 규칙을 어림짐작하지 않기.
2. **등장·퇴장만 기록하는 사고** 익히기. 구간에 똑같은 값을 누적할 때 전 범위를 전부 갱신할 필요가 있는지 질문.
3. **복잡도는 처음에만 분석하지 않기.** 풀이 아이디어를 떠올린 다음, 코드를 수정한 다음, **전체 단계의 최악 반복 횟수**를 다시 계산.
4. **더하는 값의 타입 판단.** 배열 원소가 `int`여도 합계는 `long`일 수 있음. 산술의 중간 결과도 확인.
5. **구간 경계부터 고정.** 닫힌 구간 `[L,R]`인지, 반열린 구간 `[L,R)`인지 선언하고, 첫/마지막 원소를 직접 검산.

**재풀이 목표:** `diff[start]++`, `diff[end]--`를 왜 쓸 수 있는지, 누적합이 실제 배열을 복원하는 이유, 슬라이딩 윈도우의 `-left/+right`가 올바른 이유를 코드를 보기 전에 말할 수 있을 것.
