## 1. 접근과 결과 배열의 의미

덩어리마다 BFS로 크기를 구하고, 그 덩어리가 걸친 열마다 크기를 한 번씩 더하는 접근은 타당함. 같은 덩어리가 한 열의 여러 칸에 걸쳐도 mark[c]로 중복 집계를 막은 점이 핵심임.

- result[c]: c열에 시추했을 때 얻는 총 석유량.
- visited: 전체 탐색에서 공유. 이미 처리한 석유 덩어리를 다시 탐색하지 않도록 함.
- mark와 sum: 한 덩어리를 처리하는 동안만 관리.
- 기존 “덩어리들 중 max 고르기” 주석은 “열별 총 석유량 중 최댓값 구하기”로 고치는 것이 정확함.

빈 땅까지 큐에 넣고 방문 표시하는 현재 방식도 정답에는 문제 없음. 다만 탐색할 석유만 큐에 넣으면 큐 처리와 분기가 줄어듦.

## 2. 배열 최댓값

`Arrays.stream(result).max().getAsInt()` 사용 가능함.

- max()는 OptionalInt를 반환함.
- 빈 배열이면 getAsInt()에서 예외가 발생함.
- 이 문제는 열이 최소 1개이므로 안전함.
- 시간은 O(M). 반복문과 같은 차수이고, 현재 코드에서 먼저 개선할 부분은 아님.

근거: [Java 17 IntStream.max](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/stream/IntStream.html#max())

## 3. 시간복잡도: BFS 전체 비용과 덩어리별 후처리를 분리

N은 행 수, M은 열 수, K는 덩어리 수.

| 작업 | 모든 실행의 합 |
| --- | --- |
| 이중 반복문으로 시작점 확인 | O(NM) |
| 모든 BFS의 격자 탐색 | O(NM) |
| 덩어리마다 길이 M의 mark 생성·초기화 | O(KM) |
| 덩어리마다 mark의 모든 열 확인 | O(KM) |
| result 최댓값 | O(M) |

전체는 **O(NM + KM)**. 바둑판 배치처럼 K가 NM에 비례하면 최악 **O(NM²)**.

BFS 한 번의 최대 비용과 호출 횟수의 최대를 그대로 곱하면 안 됨. 큰 덩어리 하나를 탐색한 칸은 다른 BFS에서 다시 탐색하지 않음. 각 덩어리 크기의 합은 NM 이하임.

현재처럼 큐에서 방문 여부를 검사해도 이웃 탐색 자체는 각 칸에서 한 번만 수행함. 칸마다 이웃이 최대 4개여서 중복 삽입 비용까지 포함한 BFS 전체는 O(NM).

500×500 바둑판이면 덩어리 125,000개 × 500열 = mark 후처리만 62,500,000회. 실제 시간 초과를 뜻하는 것은 아니지만 후처리 개선 효과가 큰 입력임.

원본과 개선 예시 모두 추가 공간의 최대 필요량은 O(NM). 덩어리마다 만든 mark의 누적 할당량과 동시에 필요한 공간은 구분해야 함.

## 4. 방향 배열로 상하좌우 표현하기

기존 [DFS/BFS 메모](../../../피드백/DFS&BFS.md)의 연구소 기록에도 “이동은 dx, dy로 처리하자”가 있었음. 이번에 다시 떠올린 내용을 BFS 기본 구현에 연결하기.

```java
private static final int[] DR = {-1, 1, 0, 0};
private static final int[] DC = {0, 0, -1, 1};

for (int d = 0; d < 4; d++) {
    int nr = r + DR[d];
    int nc = c + DC[d];
    // 다음 좌표 범위와 탐색 조건 확인
}
```

| d | DR[d] | DC[d] | 이동 |
| --- | ---: | ---: | --- |
| 0 | -1 | 0 | 위 |
| 1 | 1 | 0 | 아래 |
| 2 | 0 | -1 | 왼쪽 |
| 3 | 0 | 1 | 오른쪽 |

- r은 행, c는 열. 배열에서는 행 인덱스가 커지면 아래로 이동함.
- **같은 인덱스의 DR[d], DC[d]가 한 쌍**임.
- 방향 순서 자체보다 네 방향을 빠짐없이 같은 쌍으로 사용하는 것이 중요함.
- 이미 범위 안인 현재 좌표를 매번 검사할 필요 없음. 다음 좌표 nr, nc만 검사함.
- 크기는 rows, cols, 좌표는 r, c로 구분하면 혼동이 줄어듦.
- 큐는 ArrayDeque 사용. LinkedList도 가능하지만 일반적인 큐 용도에서는 ArrayDeque를 기본 선택으로 둘 수 있음.

근거: [Java 17 ArrayDeque](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/ArrayDeque.html)

## 5. visited는 큐에 넣을 때 표시

이번 디버깅 원인은 같은 좌표가 큐에 여러 번 들어갈 수 있었다는 점임.

모든 칸이 1인 2×2 격자에서:

1. (0,0)이 (0,1), (1,0)을 큐에 넣음.
2. (0,1)이 (1,1)을 큐에 넣음.
3. 아직 (1,1)을 꺼내지 않았으므로 (1,0)도 (1,1)을 다시 넣음.
4. 꺼낼 때 방문 여부 검사를 생략하면 크기를 4가 아니라 5로 셈.

현재의 `if (visited[x][y]) continue;`가 있으면 중복 집계를 막을 수 있음. 더 단순하게 구현하려면 삽입할 때 표시해서 중복 삽입 자체를 막음.

```java
visited[startR][startC] = true;
q.offer(new int[] {startR, startC});

// 이웃도 범위, 석유 여부, 방문 여부를 통과한 뒤:
visited[nr][nc] = true;
q.offer(new int[] {nr, nc});
```

visited를 “이미 발견해서 처리하기로 한 칸”으로 이해하기. 시작점에도 바로 표시해야 함.

기존 단지번호붙이기 메모에도 “start에서 한 번, offer할 때 한 번”이 있었음. 네트워크 메모의 “while 안에서 방문 확인”만으로는 시점이 불명확하므로 함께 정정함. 이 원칙은 이번 같은 일반적인 BFS/연결 요소 탐색 기준임.

## 6. mark 대신 최소·최대 열 기록

상하좌우로 연결된 한 덩어리가 2열과 5열에 걸치면, 그 사이를 연결하는 경로는 반드시 3열과 4열도 지남. 같은 행에서 이어질 필요는 없음.

따라서 덩어리가 걸친 열은 **minCol부터 maxCol까지 연속**임. BFS에서 두 값만 기록하고 그 구간에 size를 한 번씩 더할 수 있음.

마지막 구간 반복문의 전체 비용도 O(NM)임. 한 덩어리가 걸친 열 수는 그 덩어리의 칸 수 이하이고, 모든 덩어리의 칸 수 합은 NM 이하이기 때문임.

개선 예시의 전체 시간 O(NM), 추가 공간 O(NM).

```java
import java.util.*;

class Solution {
    // 같은 인덱스의 행/열 변화량을 한 쌍으로 사용: 상, 하, 좌, 우
    private static final int[] DR = {-1, 1, 0, 0};
    private static final int[] DC = {0, 0, -1, 1};

    private int[] result;
    private boolean[][] visited;

    public int solution(int[][] land) {
        int rows = land.length;
        int cols = land[0].length;
        result = new int[cols];
        visited = new boolean[rows][cols];

        for (int r = 0; r < rows; r++) {
            for (int c = 0; c < cols; c++) {
                if (land[r][c] == 1 && !visited[r][c]) {
                    bfs(land, r, c);
                }
            }
        }

        // 각 열에서 얻을 수 있는 총 석유량 중 최댓값
        return Arrays.stream(result).max().getAsInt();
    }

    private void bfs(int[][] land, int startR, int startC) {
        int rows = land.length;
        int cols = land[0].length;
        Queue<int[]> q = new ArrayDeque<>();

        visited[startR][startC] = true;
        q.offer(new int[] {startR, startC});

        int size = 0;
        int minCol = startC;
        int maxCol = startC;

        while (!q.isEmpty()) {
            int[] curr = q.poll();
            int r = curr[0];
            int c = curr[1];

            size++;
            minCol = Math.min(minCol, c);
            maxCol = Math.max(maxCol, c);

            for (int d = 0; d < 4; d++) {
                int nr = r + DR[d];
                int nc = c + DC[d];

                if (nr < 0 || nr >= rows || nc < 0 || nc >= cols) {
                    continue;
                }
                if (land[nr][nc] == 0 || visited[nr][nc]) {
                    continue;
                }

                visited[nr][nc] = true;
                q.offer(new int[] {nr, nc});
            }
        }

        // 연결된 덩어리는 최소 열과 최대 열 사이의 모든 열에 걸침.
        for (int c = minCol; c <= maxCol; c++) {
            result[c] += size;
        }
    }
}
```

## 7. 주석 회고 정리

```java
/*
풀이 시간: 38분

1. 배열 최댓값
   - Arrays.stream(arr).max().getAsInt() 사용 가능.
   - 빈 배열이면 예외가 발생하므로 길이 조건을 확인한다.
   - 최댓값 탐색은 O(배열 길이).

2. 시간복잡도
   - 반복문 모양만 보고 NM × NM으로 계산하지 않는다.
   - visited를 공유하므로 모든 BFS 탐색 비용의 합은 O(NM).
   - 덩어리마다 길이 M의 mark를 생성하고 순회하는 비용은 O(KM).
   - 전체 O(NM + KM), 최악 O(NM²).
   - 최소·최대 열을 기록하면 전체 O(NM)으로 개선 가능.

3. BFS 코드 정리
   - DR = {-1, 1, 0, 0}, DC = {0, 0, -1, 1}.
   - 같은 인덱스끼리 묶어 상·하·좌·우 이동량으로 사용한다.
   - 다음 좌표의 범위 → 석유 여부 → 방문 여부를 확인한다.
   - 탐색할 석유 칸만 ArrayDeque에 넣는다.

4. 방문 처리
   - 큐에서 꺼낼 때 표시하면 같은 칸이 중복 삽입될 수 있다.
   - 시작점을 포함해 큐에 넣을 때 방문 표시한다.
   - visited는 이미 발견해서 처리하기로 한 칸이라는 뜻.
   - 각 석유 칸이 큐에 한 번만 들어가도록 만든다.

5. 구현 전 설계
   - result[c]: c열에서 얻을 수 있는 총 석유량.
   - 전체에서 공유: visited, result.
   - 덩어리마다 새로 관리: 크기, 걸친 열 정보.
   - 한 덩어리의 크기는 해당 열마다 정확히 한 번 더한다.
   - BFS 종료 후 처리도 덩어리 수만큼 반복됨을 확인한다.
   - 2×2 전체 석유, 바둑판, 전부 빈 땅을 손으로 검증한다.
*/
```

“더 자세히 설계하기”를 다음 행동으로 구체화하기: **상태의 의미, 상태를 공유하는 범위, 방문 표시 시점, 중복 집계를 막는 방법, 덩어리별 후처리 비용을 코딩 전에 적기.**
