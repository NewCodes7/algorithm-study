- 문제: [프로그래머스 176962 / 과제 진행하기](https://school.programmers.co.kr/learn/courses/30/lessons/176962)
- 유형: 정렬, 스택, 시뮬레이션, 선점과 재개
- 최초 풀이 기록: 11:29~12:14, 45분 시점에 테스트 1개 실패. 최종 수정에 든 시간은 별도로 기록하지 않음.
- [Java 파일](./과제 진행하기.java): 직접 작성한 최종 코드와 원래 회고를 보존함. 아래 개선 제안은 원본에 적용하지 않은 학습용 내용임.

## 1. 빠른 복습

1. 새 과제는 시작 시각이 되면 무조건 시작함. 현재 과제가 남아 있으면 중단하고 스택에 저장함.
2. 현재 종료 예정 시각과 다음 시작 시각을 `< / == / >`로 나누고, 여유가 있을 때 스택 유무를 확인함.
3. 스택이 비어 있다는 것은 멈춘 과제가 없다는 뜻임. 현재 과제가 끝났다는 뜻은 아님.
4. 멈춘 과제를 재개할 때는 다음 과제를 아직 시작하지 않았으므로 `i`를 증가시키지 않음.
5. 마지막 과제도 기존 선점 규칙을 따름. 일반 로직으로 처리되는 상황에 별도 예외 분기를 만들지 않기.
6. `curr`은 현재 구간의 시작·재개 시각, `duration`은 그 시각 기준 남은 시간임.
7. 반복 횟수는 전체 `i++`와 `pop` 횟수의 합으로 계산함. 정렬 O(n log n), 시뮬레이션 O(n).
8. `hh:mm`처럼 두 자리로 고정된 형식은 문자열 사전순과 시간순이 일치함. 시간 계산은 분 단위 정수로 수행함.

## 2. 최초 오답의 원인: 마지막 과제 전용 분기

최초 코드에는 다음 분기가 있었음.

```java
if (stack.isEmpty() && i == plans.length - 1) {
    list.add(name);
    list.add(plans[i][0]);
    break;
}
```

스택이 비었고 다음 과제가 마지막이라는 사실만으로 현재 과제가 먼저 끝난다고 판단함. 하지만 마지막 과제 역시 시작 시각이 되면 현재 과제를 선점할 수 있음.

### 반례

```java
String[][] plans = {
    {"aaa", "12:00", "10"},
    {"bbb", "12:20", "30"},
    {"ccc", "12:30", "10"}
};
```

| 시각 | 동작 |
| --- | --- |
| 12:00~12:10 | aaa 완료 |
| 12:10~12:20 | 진행할 과제가 없어 대기 |
| 12:20~12:30 | bbb를 10분 진행 |
| 12:30 | bbb의 남은 20분을 저장하고 ccc 시작 |
| 12:40 | ccc 완료 후 bbb 재개 |
| 13:00 | bbb 완료 |

기대 결과: `["aaa", "ccc", "bbb"]`.

기존 분기는 `["aaa", "bbb", "ccc"]` 순서를 기록함. 또한 `break` 이후에도 반복문 밖의 `list.add(name)`이 실행되어 내부 리스트는 `["aaa", "bbb", "ccc", "bbb"]`가 됨. 앞에서 과제 수만큼만 복사하므로 중복 원소가 반환 결과에 드러나지 않았음.

최종 코드에서는 이 분기를 제거함. 마지막 과제도 기존 시간 비교로 처리하고, 반복문이 끝난 후 현재 과제와 스택을 완료 처리하면 됨.

학습 포인트:

- 예외 분기를 넣기 전에 일반 로직으로 처리할 수 있는지 확인하기.
- `break`는 반복문 종료이며 메서드 종료가 아님.
- 완료 목록에는 각 과제가 정확히 한 번씩 들어가야 함.
- 결과 길이뿐 아니라 중복과 누락도 확인하기.

## 3. 분기 설계: 비교 기준부터 정하기

“분기를 최대한 꼼꼼하게 생각하기”를 다음 행동으로 구체화하기.

> 현재 과제의 종료 예정 시각과 다음 과제의 시작 시각을 비교하고, 가능한 관계를 빠짐없이 나눈다.

```java
int endTime = curr + duration;
int nextStart = time;
```

| 조건 | 처리 | 다음 과제 인덱스 |
| --- | --- | --- |
| nextStart < endTime | 남은 시간을 스택에 저장하고 새 과제 시작 | 증가 |
| nextStart == endTime | 현재 과제를 완료하고 새 과제 시작 | 증가 |
| nextStart > endTime, 스택 있음 | 현재 과제를 완료하고 멈춘 과제 재개 | 유지 |
| nextStart > endTime, 스택 없음 | 현재 과제를 완료하고 다음 시작 시각까지 대기한 뒤 새 과제 시작 | 증가 |

종료 시각과 시작 시각이 같으면 현재 과제는 완료된 것으로 처리함. 이때 새 과제가 멈춘 과제보다 우선함.

먼저 시간 관계를 세 가지로 나누고, 여유가 있는 경우에만 스택 상태로 나누면 경우를 하나씩 떠올리는 방식보다 누락을 줄이기 쉬움.

## 4. 잘 처리한 부분과 상태의 의미

### 재개할 때 i를 유지하기

```java
list.add(name);
String[] suspended = stack.pop();
name = suspended[0];
curr = curr + duration;
duration = Integer.parseInt(suspended[1]);
continue;
```

현재 과제의 완료 시각부터 멈춘 과제를 재개함. `curr`을 갱신할 때는 아직 기존 과제의 `duration`을 사용하고, 그다음 재개할 과제의 남은 시간을 대입함.

다음 반복에서 같은 `plans[i]`를 기준으로 다시 비교하므로, 다음 과제가 시작되기 전까지 멈춘 과제를 여러 개 연속으로 완료할 수 있음. 재개한 과제가 시간이 부족하면 다시 중단하는 상황도 처리됨.

### 반복문 종료 후 처리

`i == plans.length`이면 모든 예정 과제가 이미 시작된 상태임. 이후에는 새 과제의 선점이 없으므로 현재 과제를 먼저 끝내고 스택을 위에서부터 완료하면 됨. 완료 순서만 필요하므로 이 단계에서는 남은 시간 계산을 생략할 수 있음.

### 변수명과 주석

| 변수 | 의미 | 이름 제안 |
| --- | --- | --- |
| curr | 현재 과제를 시작하거나 재개한 시각 | currentTime |
| duration | 그 시각을 기준으로 남은 작업 시간 | remainingTime |
| time | 다음 과제의 시작 시각 | nextStart |
| i | 아직 시작하지 않은 다음 과제 인덱스 | nextIndex |
| list | 과제가 완료된 순서 | completed |

반복 시작 시, 각 과제는 완료 목록·현재 과제·스택·아직 시작하지 않은 구간 중 한 곳에만 속해야 함. 전체 개수가 n인지, 같은 과제가 두 곳에 동시에 들어가지는 않았는지로 상태를 점검할 수 있음.

주석으로 분기를 구분한 점은 좋음. 다음처럼 시간 관계를 직접 표현하면 더 명확함.

```java
// 현재 과제가 끝나기 전에 새 과제가 시작됨
// 현재 과제 종료와 새 과제 시작이 동시에 발생함
// 다음 과제 시작까지 여유가 있으므로 멈춘 과제를 재개함
```

## 5. Java 구현 개선 제안

최종 코드의 알고리즘을 바꿀 필요는 없음. 아래는 가독성과 자료 표현을 위한 선택적 개선임.

### 내부 데이터는 의미에 맞는 타입으로 저장하기

입력이 `String[][]`이라고 해서 스택 내부의 남은 시간까지 문자열로 저장할 필요는 없음.

```java
static class PausedTask {
    String name;
    int remainingTime;

    PausedTask(String name, int remainingTime) {
        this.name = name;
        this.remainingTime = remainingTime;
    }
}
```

이름과 남은 시간을 묶고, 남은 시간은 int로 보관함.

```java
Deque<PausedTask> stack = new ArrayDeque<>();
stack.push(new PausedTask(name, endTime - nextStart));

PausedTask suspended = stack.pop();
name = suspended.name;
duration = suspended.remainingTime;
```

불필요한 `Integer.toString`과 `Integer.parseInt` 왕복을 없애고 `suspended[1]`의 의미를 필드명으로 드러내는 것이 주된 목적임.

### Stack 대신 Deque

Java 공식 문서는 기존 Stack 클래스보다 Deque 사용을 권장함. ArrayDeque를 스택 구현으로 선택할 수 있고, push/pop/peek 사용법은 유지됨.

기존 자료 형태를 유지하면서 선언만 먼저 바꿀 수도 있음.

```java
Deque<String[]> stack = new ArrayDeque<>();
```

근거: [Java 17 Deque](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Deque.html)

### 배열 반환 간소화

별도 answer 배열 선언과 마지막 복사 반복문을 제거하고 다음처럼 반환 가능함.

```java
return list.toArray(new String[0]);
```

### 시간 정렬과 중복 변환

`hh:mm` 형식에서는 시와 분이 모두 두 자리로 고정되어 있어 `a[1].compareTo(b[1])`로 정렬해도 시간순이 됨. `"9:00"`처럼 자릿수가 일정하지 않으면 그대로 적용할 수 없음.

마지막 분기의 `curr = convert(arr[1]);`는 이미 계산한 `curr = time;`으로 바꿀 수 있음. 현재 코드의 정답에는 영향이 없는 작은 정리임.

## 6. 시간·공간 복잡도

n은 과제 수.

| 작업 | 전체 비용 |
| --- | --- |
| 시작 시각 정렬 | O(n log n) |
| 시뮬레이션 | O(n) |
| 마지막 스택 정리와 결과 배열 복사 | O(n) |
| 전체 시간 | O(n log n) |
| 추가 공간 | O(n) |

while에서 i가 증가하지 않는 반복이 있다고 해서 O(n²)이 되는 것은 아님.

- 반복마다 i가 증가하거나 스택에서 과제를 하나 꺼냄.
- i의 증가 횟수는 최대 n - 1번.
- push는 새 과제가 현재 과제를 선점할 때만 발생하므로 전체 최대 n - 1번.
- pop 총횟수도 push 총횟수를 넘을 수 없음.
- 같은 과제가 여러 번 중단될 수 있어도 전체 중단 횟수는 새 과제의 시작 횟수에 제한됨.

반복문 한 번의 최대 비용과 반복 횟수를 막연하게 곱하지 말고, 전체에서 각 동작이 몇 번 발생하는지 세기.
