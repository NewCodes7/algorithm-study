# 문자열 압축 재풀이 피드백 — 2026-09-19

- 문제: [프로그래머스 60057 문자열 압축](https://school.programmers.co.kr/learn/courses/30/lessons/60057)
- 유형: 완전탐색 + 문자열 구현 + 연속 구간 묶기
- 풀이 시간: 본인 기록 기준 약 30분
- 이번 Java 파일: 사용자가 제공한 최종 코드와 회고를 보존함. 빈 줄과 들여쓰기만 정리함.
- 검증: Java 17에서 현재 코드와 아래 개선 예시 모두 2,264건 통과. 프로그래머스에 직접 제출한 결과는 아님.

## 1. 종합 평가

압축 단위를 전부 시도하고, 같은 토큰이 연속되는 구간만 묶는 접근은 문제 조건에 맞음. 현재 최종 코드에서 오답 원인은 발견하지 못했음. 개선의 우선순위는 새로운 알고리즘 습득보다 구현 중 관리해야 하는 상태를 줄이는 것임.

잘한 점:

- 문자열의 첫 위치부터 고정 길이로 자른다는 조건을 정확히 반영함.
- 첫 토큰을 미리 정해 첫 비교의 기준을 명확하게 만듦.
- String.equals로 내용을 비교하고 StringBuilder로 결과를 누적함.
- append(count)를 사용하여 10, 100, 1000처럼 반복 횟수의 자릿수가 늘어나는 경우도 자연스럽게 처리함.
- 마지막 완성된 묶음과 짧은 나머지를 모두 반영함.
- 디버깅 원인을 직접 기록함. 다음 연습에서 확인할 행동으로 연결할 수 있음.

복잡도:

- 압축 단위 후보 O(n)개, 후보 하나의 처리 O(n) → 전체 O(n²).
- 길이 k의 토큰 복사·비교는 O(k)지만, 한 후보에서 토큰 수가 약 n/k개라 합쳐 O(n). 별도 세제곱이 아님.
- 동시에 필요한 배열·버퍼·문자열 공간은 O(n).
- n ≤ 1,000이라는 문제 제한에 적절한 접근임.

## 3. 세 가지 디버깅 원인과 예방

### 3-1. delete의 끝 인덱스는 포함하지 않음

`delete(start, end)`는 [start, end) 범위를 삭제함.

```java
StringBuilder sb = new StringBuilder("abc");
sb.delete(0, sb.length() - 1); // delete(0, 2) → "c"가 남음
```

- 길이 1이면 delete(0, 0)이 되어 아무것도 지우지 않음.
- 빈 버퍼면 delete(0, -1)이 되어 예외가 발생함.
- 모두 비우려면 `sb.setLength(0)` 또는 `sb.delete(0, sb.length())` 사용.
- substring도 끝 인덱스는 제외함. 유효한 마지막 문자 인덱스가 n-1이어도 범위의 끝은 n이 될 수 있음.

근거: [Java 17 StringBuilder 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/StringBuilder.html#delete(int,int))

### 3-2. 마지막에는 서로 다른 두 종류의 미처리 데이터가 남음

현재 코드에서 내부 반복문이 끝났을 때:

| 변수 | 의미 |
| --- | --- |
| str | 이미 확정하여 결과에 넣은 묶음들 |
| before + count | 아직 결과에 넣지 않은 마지막 완성 토큰의 연속 묶음 |
| sb | 단위 길이를 채우지 못한 마지막 조각. 없으면 빈 문자열 |

예: `s = "abcabcde"`, 단위 길이 3.

| 시점 | str | before | count | sb |
| --- | --- | --- | --- | --- |
| 첫 토큰 설정 후 | "" | "abc" | 1 | "" |
| 두 번째 "abc" 처리 후 | "" | "abc" | 2 | "" |
| 모든 문자 순회 후 | "" | "abc" | 2 | "de" |
| 마지막 처리 후 | "2abcde" | "abc" | 2 | "de" |

따라서 마지막에는 **미확정 묶음 "2abc"와 짧은 조각 "de"를 각각 한 번씩** 추가해야 함. 결과에 추가해도 sb의 내용이 자동으로 지워지지는 않음.

실제 실행 예시를 적어보겠다는 자기 피드백은 적절함. 다만 평범한 입력 하나보다 다음 세 경계를 의도적으로 고르는 게 효과적임.

- 마지막까지 같은 토큰: `"abab"`, size=2.
- 짧은 나머지가 남음: `"ababx"`, size=2.
- 다음 압축 단위로 넘어감: 앞 후보의 sb 내용이 새 후보에 남지 않는지 확인.

### 3-3. 초기화를 기억하는 대신 변수 수명을 줄이기

현재 구조는 sb와 str을 후보 반복문 밖에서 생성하므로 매 후보가 끝날 때 비워야 함. 초기화 한 줄을 빠뜨리면 다음 후보가 이전 데이터를 이어받음.

최소 변경으로 예방하려면:

```java
for (int size = 1; size <= s.length(); size++) {
    StringBuilder tokenBuffer = new StringBuilder();
    StringBuilder compressed = new StringBuilder();
    // 이 후보에 필요한 처리
}
```

이렇게 바꾸면 후보 사이 초기화는 필요 없어짐. 문자 단위로 토큰을 만드는 구조를 유지한다면, 한 후보 안에서 토큰 완성 후 tokenBuffer를 비우는 작업은 여전히 필요함.

변수명 개선도 도움이 되지만 초기화 누락 자체를 막지는 못함. **변수명 → 변수 범위 → 처리 단위** 순서로 구조를 개선하면 효과가 커짐.

## 4. 권장 리팩토링

아래 코드는 별도 학습용 예시임. 저장소의 Java 풀이 파일은 사용자가 작성한 이번 버전을 유지함.

- size만큼 이동하며 substring으로 토큰을 얻음.
- Math.min으로 짧은 마지막 조각까지 하나의 토큰으로 읽음.
- 짧은 조각은 앞의 완성 토큰과 길이가 달라 같을 수 없으므로 기존 분기에서 자연스럽게 처리됨.
- 한 후보의 변수는 compressedLength 안에서만 존재함.
- 마지막 미확정 묶음을 한 번 반영하는 작업은 여전히 필요함.
- 반복 횟수가 1이면 숫자는 생략함.

```java
class Solution {
    public int solution(String s) {
        int answer = s.length();

        for (int size = 1; size <= s.length() / 2; size++) {
            answer = Math.min(answer, compressedLength(s, size));
        }
        return answer;
    }

    private int compressedLength(String s, int size) {
        StringBuilder result = new StringBuilder();
        String previous = s.substring(0, size);
        int count = 1;

        for (int start = size; start < s.length(); start += size) {
            String current =
                    s.substring(start, Math.min(start + size, s.length()));

            if (previous.equals(current)) {
                count++;
            } else {
                appendGroup(result, previous, count);
                previous = current;
                count = 1;
            }
        }

        appendGroup(result, previous, count);
        return result.length();
    }

    private void appendGroup(StringBuilder result, String token, int count) {
        if (count > 1) {
            result.append(count);
        }
        result.append(token);
    }
}
```

size > n/2이면 완전한 토큰 두 개가 들어갈 수 없으므로 반복 압축이 일어나지 않음. 따라서 answer를 원래 길이 n으로 시작하고 n/2까지만 확인하면 됨. n=1이면 반복문을 실행하지 않고 1을 반환함.

n/2까지 줄여도 시간복잡도는 O(n²)로 동일함. 이번 학습에서는 이 최적화보다 토큰 단위 순회와 변수 범위가 더 중요함.

추가로 길이만 필요하므로 결과 문자열 대신 아래 길이를 더할 수도 있음.

```java
length += token.length();
if (count > 1) {
    length += String.valueOf(count).length();
}
```

필수 최적화는 아님. 우선 위처럼 동작을 눈으로 확인하기 쉬운 구현을 익히는 것이 좋음. 토큰을 substring으로 생성한다면 결과 StringBuilder를 없앴다고 공간복잡도가 곧바로 O(1)이 되는 것도 아님.

## 5. 사소하지만 정리할 부분

- `answer = 0`과 `answer == 0` 조건은 현재 정답에는 문제 없음. `answer = s.length()`와 `Math.min`으로 바꾸면 의미가 더 직접적임.
- `// 최댓값` 주석은 실제 동작상 최솟값임.
- 서로 다른 토큰을 처리할 때 sb.toString()을 비교와 대입에서 두 번 호출함. current 지역 변수에 한 번 저장할 수 있음.
- 권장 이름: i → size, j → index 또는 start, sb → tokenBuffer, str → compressed, before → previous, count → repeatCount.
- 첫 토큰을 미리 생성하는 현재 방식은 타당함. 반드시 빈 문자열에서 시작하는 방식으로 바꿀 필요 없음.

## 7. 다음 풀이에서 적용할 짧은 루틴

코딩 전 1분:

1. “한 번의 반복은 무엇을 처리하는가?” → 이 문제는 토큰 하나.
2. “아직 결과에 반영되지 않은 데이터는 무엇인가?” → previous와 count.
3. “반복 종료 후 무엇을 한 번 더 반영해야 하는가?” → 마지막 묶음.
4. “다음 후보에 남아서는 안 되는 변수는 어디서 생성할 것인가?” → 후보 메서드 내부.

복습 완료 기준:

- 하루나 이틀 뒤, 이전 코드를 보지 않고 토큰 단위 순회로 다시 작성함.
- `"abab"`, `"ababx"`, 길이 1, 같은 문자 10회 반복을 직접 확인함.
- 매번 “더 조심하기”를 다짐하는 대신 초기화 책임과 별도 예외 분기가 적은 구조로 작성함.
