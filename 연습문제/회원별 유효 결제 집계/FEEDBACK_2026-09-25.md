# 회원별 유효 결제 집계 풀이 피드백 — 2026-09-25

## 복습 요약

- 문자열 형식 검증과 문자열 정규화는 순서가 중요하다. 먼저 원본 MEMO가 유효한지 REGEXP로 확인한 뒤 하이픈을 제거한다.
- 같은 전화번호가 01012345678과 010-1234-5678 두 형식으로 들어올 수 있으므로 원본 MEMO가 아니라 정규화된 전화번호 기준으로 GROUP BY해야 한다.
- 모든 회원을 남겨야 하므로 MEMBERS를 기준으로 LEFT JOIN한다.
- 결제가 없는 회원은 집계 CTE에 행이 없어서 NULL이 되므로 COALESCE(..., 0)으로 출력값을 맞춘다.
- 금액이 0이어도 TX_ID가 존재하는 유효 이벤트이므로 COUNT에 포함된다.
- 날짜 구간은 >= 시작 AND < 다음 달 시작 형태로 두면 경계 처리가 명확하다.

## 최종 SQL

[SQL 파일](./회원별%20유효%20결제%20집계.sql)

~~~sql
WITH PAY AS (
  SELECT
    REPLACE(SUBSTRING(MEMO, 5), '-', '') AS PHONE,
    COUNT(TX_ID) AS PAY_COUNT,
    SUM(AMOUNT) AS TOTAL_AMOUNT
  FROM PAYMENT_LOG
  WHERE MEMO REGEXP '^PAY:010([0-9]{8}|-[0-9]{4}-[0-9]{4})$'
    AND PAID_AT >= '2026-09-01 00:00:00'
    AND PAID_AT < '2026-10-01 00:00:00'
  GROUP BY PHONE
)
SELECT
  A.MEMBER_ID,
  COALESCE(B.PAY_COUNT, 0) AS PAY_COUNT,
  COALESCE(B.TOTAL_AMOUNT, 0) AS TOTAL_AMOUNT
FROM MEMBERS A
LEFT JOIN PAY B
  ON B.PHONE = REPLACE(A.PHONE, '-', '')
ORDER BY TOTAL_AMOUNT DESC, A.MEMBER_ID;
~~~

## 잘한 점

### 1. CTE로 유효 결제를 먼저 좁힌 구조

처음부터 PAYMENT_LOG 전체를 MEMBERS와 복잡하게 조인하지 않고, 기간과 메모 형식을 먼저 걸러 PAY로 집계하려 한 구조는 좋았다.
필터 → 집계 → 전체 회원과 LEFT JOIN이라는 단계가 분리되어 읽기 쉽다.

### 2. 날짜 범위를 반열린 구간으로 정확히 처리

~~~sql
PAID_AT >= '2026-09-01 00:00:00'
AND PAID_AT < '2026-10-01 00:00:00'
~~~

9월 30일 23:59:59는 포함하고 10월 1일 00:00:00은 제외한다.
날짜/시간 범위 문제에서 다음 구간의 시작을 미만으로 두는 습관을 유지한다.

### 3. REGEXP 자체는 빠르게 복구함

처음에는 정규표현식을 거의 잊은 상태였지만 다음 문법을 복습한 뒤 문제 패턴을 직접 구성했다.

- ^ : 문자열 시작
- $ : 문자열 끝
- [0-9] : 숫자 한 자리
- {n} : 정확히 n번
- (A|B) : A 또는 B

최종 패턴:

~~~text
^PAY:010([0-9]{8}|-[0-9]{4}-[0-9]{4})$
~~~

^와 $를 빠뜨리면 앞부분만 맞는 잘못된 문자열도 매칭될 수 있으므로 전체 형식 검증 문제에서는 시작·끝을 함께 확인한다.

## 처음 풀이에서 수정한 점

### 1. 원본 MEMO 기준 GROUP BY

초안:

~~~sql
SELECT REPLACE(SUBSTRING(MEMO, 5), '-', '') AS MEMO,
       COUNT(TX_ID) AS PAY_COUNT,
       SUM(AMOUNT) AS TOTAL_AMOUNT
FROM PAYMENT_LOG
...
GROUP BY MEMO
~~~

문제점은 같은 회원의 결제가 아래 두 형식으로 들어올 수 있다는 것.

~~~text
PAY:010-1234-5678
PAY:01012345678
~~~

원본 MEMO 기준으로 그룹화하면 서로 다른 그룹으로 갈라질 수 있다.
비교 기준이 전화번호라면 먼저 동일한 표현으로 정규화하고 그 키를 기준으로 집계해야 한다.

최종:

~~~sql
REPLACE(SUBSTRING(MEMO, 5), '-', '') AS PHONE
...
GROUP BY PHONE
~~~

또한 원본 컬럼 MEMO와 가공 결과 alias를 둘 다 MEMO라고 부르면 읽을 때 의미가 섞인다.
가공 결과는 PHONE처럼 별도 의미를 드러내는 이름으로 둔다.

### 2. LIKE로 회원을 연결한 부분

초안:

~~~sql
LEFT JOIN PAY B ON B.MEMO LIKE A.PHONE
~~~

당시 PAY의 MEMO에는 PAY: 접두사가 남아 있었으므로 회원 PHONE과 그대로 매칭되지 않는다.
그리고 이 문제는 패턴 검색이 아니라 정규화한 두 전화번호가 같은지 확인하는 것이므로 LIKE보다 =가 맞다.

최종:

~~~sql
LEFT JOIN PAY B
  ON B.PHONE = REPLACE(A.PHONE, '-', '')
~~~

### 3. 전화번호 형식이 양쪽에서 같다고 가정한 점

풀이 중 "고객 번호에 대시가 붙어 있으면 거래 메모에도 붙어 있다고 가정"했지만 문제는 그 가정을 허용하지 않는다.

예:

~~~text
MEMBERS.PHONE  = 010-1234-5678
PAYMENT_LOG    = PAY:01012345678
~~~

이 둘도 같은 회원이다.
서로 다른 표현을 그대로 비교하지 말고 비교 전에 canonical form으로 맞추는 문제였다.

### 4. 최종 정렬

문제 요구는 TOTAL_AMOUNT 내림차순 → MEMBER_ID 오름차순이다.
B.TOTAL_AMOUNT에는 결제가 없는 회원의 경우 NULL이 남지만 출력에서는 COALESCE로 0이 된다.
따라서 최종 출력 alias 기준으로 정렬하면 의도가 정확하다.

~~~sql
ORDER BY TOTAL_AMOUNT DESC, A.MEMBER_ID
~~~

## SUBSTRING / REPLACE 복습

### SUBSTRING

~~~sql
SUBSTRING(문자열, 시작위치)
SUBSTRING(문자열, 시작위치, 길이)
~~~

MySQL 문자열 위치는 1부터 시작한다.

~~~sql
SUBSTRING('PAY:010-1234-5678', 5)
-- 010-1234-5678
~~~

이번 문제에서는 PAY: 네 글자를 제거하는 데 사용했다.

### REPLACE

~~~sql
REPLACE(문자열, 찾을문자열, 바꿀문자열)
~~~

~~~sql
REPLACE('010-1234-5678', '-', '')
-- 01012345678
~~~

빈 문자열로 교체하면 사실상 해당 문자를 제거한다.

이번 조합:

~~~sql
REPLACE(SUBSTRING(MEMO, 5), '-', '')
~~~

MEMO에서 PAY:를 잘라낸 뒤 하이픈을 제거해 비교 가능한 전화번호를 만든다.

## 문자열 검증과 정규화의 순서

다음 잘못된 메모가 있다고 하자.

~~~text
PAY:010-12345678
~~~

하이픈을 먼저 전부 제거하면:

~~~text
PAY:01012345678
~~~

정상 형식처럼 보이게 된다.
따라서 정규화 전에 반드시 원본 문자열이 허용된 형식인지 검증한다.

~~~text
원본 MEMO
→ REGEXP 형식 검증
→ 전화번호 추출
→ 하이픈 제거
→ JOIN / GROUP BY
~~~

## COALESCE와 alias

~~~sql
COALESCE(B.PAY_COUNT, 0) AS PAY_COUNT
~~~

COALESCE를 썼다고 AS가 반드시 필요한 것은 아니다.
다만 출력 열 이름을 PAY_COUNT로 요구하므로 alias를 붙이는 게 맞다.
MySQL에서는 AS 키워드는 생략할 수 있지만 코테에서는 명확성을 위해 AS를 적는 편이 좋다.

## SELECT alias를 사용할 수 있는 절

MySQL 기준으로 SELECT에서 만든 열 alias는 GROUP BY, HAVING, ORDER BY에서 사용할 수 있다.
WHERE에서는 사용할 수 없다.

~~~sql
SELECT
  REPLACE(PHONE, '-', '') AS NORMAL_PHONE,
  COUNT(*) AS CNT
FROM MEMBERS
GROUP BY NORMAL_PHONE
HAVING CNT >= 2
ORDER BY CNT DESC;
~~~

WHERE는 그룹화·SELECT 결과가 만들어지기 전의 개별 행을 거르는 절이므로 SELECT alias나 COUNT 같은 집계 결과를 조건으로 사용할 수 없다.

학습용 논리 순서:

~~~text
FROM / JOIN
→ WHERE
→ GROUP BY
→ 집계
→ HAVING
→ SELECT
→ ORDER BY
~~~

이는 쿼리를 이해하기 위한 논리적 순서이며 실제 물리 실행 계획을 그대로 뜻하지는 않는다.

## COUNT 관련

PAYMENT_LOG.TX_ID는 PRIMARY KEY이므로 NULL이 아니다.

따라서 이 문제의 CTE에서는:

~~~sql
COUNT(TX_ID)
~~~

와

~~~sql
COUNT(*)
~~~

의 결과가 같다.

AMOUNT가 0이어도 TX_ID가 존재하므로 건수에 정상적으로 포함된다.
0은 NULL이 아니다.

## 이번 문제에서 가져갈 행동강령

- 형식 검증과 형식 통일을 구분한다. 검증을 먼저 하고 정규화한다.
- JOIN 키의 표현 형식이 다를 수 있으면 양쪽을 같은 canonical form으로 바꾼다.
- GROUP BY 기준은 원본 표현이 아니라 문제에서 정의한 동일성 기준으로 잡는다.
- 모든 기준 행을 보존해야 하면 어느 테이블이 LEFT JOIN의 왼쪽이어야 하는지 먼저 결정한다.
- COALESCE를 적용했다면 정렬도 최종 출력값 기준인지 확인한다.
- SQL 제출 전 출력 열 이름 → NULL 처리 → 정렬 순서를 마지막에 따로 점검한다.

## 최초 풀이

~~~sql
WITH PAY AS (
  SELECT MEMO, COUNT(TX_ID) AS PAY_COUNT, SUM(AMOUNT) AS TOTAL_AMOUNT
  FROM PAYMENT_LOG
  WHERE MEMO REGEXP '^PAY:010([0-9]{8}|-[0-9]{4}-[0-9]{4})$'
  AND PAID_AT >= '2026-09-01 00:00:00' AND PAID_AT < '2026-10-01 00:00:00'
  GROUP BY MEMO
)
SELECT A.MEMBER_ID, COALESCE(B.PAY_COUNT, 0) AS PAY_COUNT, COALESCE(B.TOTAL_AMOUNT, 0) AS TOTAL_AMOUNT
FROM MEMBERS A
LEFT JOIN PAY B ON B.MEMO LIKE A.PHONE
ORDER BY A.MEMBER_ID, B.PAY_COUNT, B.TOTAL_AMOUNT DESC
~~~

이후 SUBSTRING과 REPLACE를 학습해 전화번호를 정규화하고 JOIN을 = 비교로 수정했다.

## 검증

보강된 연습 데이터 기준으로 최종 관계 연산 결과를 별도 실행해 확인했다.

~~~text
MEMBER_ID | PAY_COUNT | TOTAL_AMOUNT
2         | 2         | 25000
1         | 3         | 20000
6         | 1         | 20000
3         | 1         | 0
4         | 0         | 0
5         | 0         | 0
7         | 0         | 0
8         | 0         | 0
~~~

검증은 SQLite에 REGEXP 함수를 별도로 등록하고 MySQL SUBSTRING과 동등한 SUBSTR 표현을 사용해 결과 관계를 확인했다.
MySQL 8.0 서버에서 이 파일을 직접 실행한 검증은 하지 않았다.
